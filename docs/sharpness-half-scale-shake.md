# 1/2 크기 재판정의 흔들림 근거 보완(판정 규칙 5)

평가일: 2026-11-17. 기준 커밋: `49b0d08`(`main`, 판정 규칙 4). Issue #27. [공개 실제 사진 평가](sharpness-real-photo-evaluation.md)와 [브라우저 독립 축소](sharpness-browser-consistency.md)의 후속 기록이다.

## 요약

- 변경: 판정 근거가 부족해 1/2 크기에서 다시 볼 때(판정 규칙 3)만, 흔들림 근거 구역의 **수직 방향 선명 조건**을 보완한다. 수직 방향 윤곽이 잡음 기준에 못 미쳐도 미세 경계에서 잡음 몫(6σ²)을 빼고 비율이 임계값 이상이면 선명 근거로 본다.
- 바꾸지 않은 것: 분석 크기의 측정·판정, 임계값 `0.025`, 흔들림 근거의 나머지 조건(근거 구역 6개·행 3·열 3 이상, 반대 구역 0개, 모든 방향이 흐린 구역 제한, 수직 방향 전체 점수 선명), 초점 불량 기준, 판정 규칙 3·4.
- 결과(공개 실제 사진, 분석용 이미지 캐시 재판정, Chromium·WebKit 같음): Kwentar 움직임 흐림 검출 **개선용 8 → 28장, 최종 검증용 6 → 26장(3.8% → 16.6%)**. 선명 정답 사진의 판정은 모든 묶음에서 바뀌지 않았다(오탐 0 → 0). 바뀐 판정은 모두 흐림 정답의 `분석 불가 → 흔들림 의심`이다.
- 한계: 효과는 크게 휘두른 흔들림(Kwentar)에 몰려 있다. 짧은 실제 손떨림(RealBlur 702장)은 0.6% → 0.7%(+1장)로 거의 개선되지 않았다. 실제 iPhone Safari에서는 실행하지 않았다.

## 1. 기준값(판정 규칙 4)

각 칸은 `흐림 판정 / 선명 판정 / 분석 불가`다.

## 2. 원인(dev)

1. **분석 불가는 윤곽이 없어서가 아니라 잡음 기준 때문이다.** 분석 불가 사진의 판정하지 못한 방향을 나누면 대부분 “윤곽 있는 구역은 3개 이상인데 잡음 기준 `max(30, 960σ²)`을 넘는 구역이 3개 미만”이다.

   | dev 분석 불가 | 사진 | 방향(사진 × 4) 중 윤곽 없음 / 잡음 기준 탈락 / 판정 | 잡음 기준 중앙값 |
   |---|---:|---|---:|
   | Kwentar 선명 | 119 | 0 / 350 / 126 | 2,184 |
   | Kwentar 초점 흐림 | 148 | 44 / 403 / 145 | 475 |
   | Kwentar 움직임 흐림 | 143 | 66 / 345 / 161 | 678 |
   | RealBlur 선명 | 157 | 0 / 264 / 364 | 771 |
   | RealBlur 흔들림 | 185 | 3 / 449 / 288 | 1,977 |

2. **판정 규칙 3(1/2 크기 재판정)은 움직임 흐림을 거의 잡지 못한다.** dev 분석 불가 움직임 흐림 143장의 1/2 크기 판정은 분석 불가 97장, 선명 46장, 흐림 0장이었다.
3. **흔들림 근거가 실제 사진에서 성립하지 않는다.** 근거 구역은 “수직 방향은 잡음 기준을 넘게 선명”해야 하는데, 흔들린 사진의 수직 방향 윤곽도 대부분 잡음 기준 아래였다. 그래서 근거 구역이 0~5개에 그친다.
4. **`선명`으로 놓친 움직임 흐림**(dev 42장)은 모든 방향을 판정했고 점수가 임계값 위다(중앙값 0.109). 분석 크기에서 흐림 근거가 보이지 않는 기존 한계다. 이번 변경은 이 사진들을 다루지 않는다.

## 4. 채택한 규칙(판정 규칙 5)

- `measureSharpness`가 판정 규칙 3으로 1/2 크기를 잴 때만 흔들림 근거 수집에 그 크기의 추정 잡음 σ를 넘긴다(`shakeAcrossNoise`).
- 근거 구역의 수직 방향 선명 조건: 윤곽이 잡음 기준 이상이면 기존처럼 비율 ≥ `0.025`. 잡음 기준 미만이고 윤곽이 `30` 이상이면 `(미세 경계 분산 − 6σ²) / 윤곽 ≥ 0.025`. 6σ²은 같은 크기의 독립 잡음이 [1, −2, 1] 차분에 더하는 분산이다(기존 `SECOND_DIFFERENCE_NOISE_GAIN`). 새 상수는 없다.
- 반대 구역(끌린 방향이 선명한 구역) 기준과 나머지 조건은 그대로라 근거가 늘어도 다른 조건이 모두 맞아야 흔들림이다.
- 1/2 크기의 흐림은 여전히 원인 근거가 일치할 때만 받아들인다(판정 규칙 3). 분석 크기에서 이미 `선명`·`흐림`이면 1/2 크기는 재지 않으므로 판정 변화는 `분석 불가 → 흔들림 의심`뿐이다. **분석 불가를 선명으로 바꾸는 경로는 없다.**
- `SHARPNESS_CLASSIFIER_REVISION` 4 → 5. 평가 내보내기 형식·설정값·사진별 필드는 같다. 판(`classifierRevision`)만 5로 기록된다.
- 추가 계산은 없다(1/2 크기는 원래 판정 규칙 3에서 재던 것). 캐시 재판정 시간 64.2 → 62.1ms/장(같은 PC의 다른 시각, 차이는 실행 오차 범위).

### 합성 장면과 기존 테스트

- 기존 단위 테스트는 기대값 변경 없이 통과한다. E2E 합성 사진 12개의 판정·원인을 제품 축소기로 Node에서 재현했을 때 모두 같았다(브라우저 E2E는 `npm run verify` 결과 참고).
- 합성 선명 장면 50개: 바뀐 장면 0개.
- 1024×768 합성 흔들림(가로·세로, 길이 15·25·41화소, 잡음 σ0.6~1.5, seed 3개, 90장): 바뀐 16장 모두 `분석 불가 → 흔들림 의심`. 잡음 σ1.5에서 25화소 6/6, 41화소 4/6이 새로 검출된다. 잡음 σ1의 25화소 흔들림은 6장 중 1장만 바뀌어 기존 한계 테스트(`blurDetectionLimits.test.ts`, 잡음 1, seed 13 → 분석 불가)는 그대로다.
- 회귀 테스트: `sharpness.test.ts`의 잡음 σ1.5·25화소 흔들림(가로·세로, seed 3개)은 판정 규칙 4에서 분석 불가, 규칙 5에서 흔들림 의심이다. 분석 크기의 흔들림 근거는 성립하지 않고 1/2 크기 근거만 성립함을 함께 확인한다.

### 제품 경로(브라우저)

보관한 Kwentar 원본을 판정 규칙 5 코드의 제품 경로(`createSharpnessWorkerAnalyzer().measure()`, `scripts/blur-eval/runInBrowser.mjs`, 100장 묶음마다 새 Vite 서버·브라우저)로 실행했다. 비교 기준은 같은 사진의 판정 규칙 4 캐시 재판정이다.

| 브라우저 | 실행 | 바뀐 판정 | 흐림 판정(규칙 4 → 5) | 선명 정답 오탐 | `failed`·`timeout` |
|---|---|---|---|---|---:|
| Chromium(Desktop Chrome, `worker`) | 1,050장 전부 | dev 움직임 흐림 20장, holdout 20장 `분석 불가 → 흔들림 의심` | 움직임 흐림 dev 8 → 28, holdout 6 → 26 | 0 → 0 | 0 |
| WebKit(iPhone 15 설정, `main-thread-decode`) | **700장(묶음 000~006)** | dev 움직임 흐림 9장, holdout 8장 `분석 불가 → 흔들림 의심` | 실행한 사진 중 움직임 흐림 dev 5 → 14, holdout 5 → 13 | 0 → 0 | 0 |

- 제품 경로 판정은 캐시 재판정과 사진 단위로 같았다. 다른 1장(`kwentar-201-motion`)은 [브라우저 독립 축소 기록](sharpness-browser-consistency.md) 3절의 1/256 고정소수점 경계 사진이다. 캐시 재판정은 규칙 4·5 모두 `선명`이고, 제품 경로는 규칙 3(2026-11-13 실행)과 규칙 5 모두 `분석 불가`라 이번 변경과 관계없다.
- 두 브라우저를 모두 실행한 700장의 판정·원인은 700/700 같다.

- 분석 시간(사진당, Worker·메인 스레드 디코딩 포함): Chromium 중앙값 388ms·95% 545ms·최대 743ms, WebKit(700장) 470·709·1,045ms. 2026-11-13 같은 사진의 규칙 3 실행(637·928·1,087ms, 742·1,071·1,510ms)보다 짧지만 시스템 부하가 다른 시각의 측정이라 개선으로 보지 않는다. 규칙 5는 계산을 더하지 않는다. 실제 휴대폰은 측정하지 않았다.

## 6. 안전성과 롤백

- 오탐 위험: 선명 정답 1,052장(Kwentar 350 + RealBlur 702)과 파생 350장에서 변화 0장. 이 원인의 오탐률 상한은 Wilson 95% 기준 약 0.4%(0/1,052)이며 휴대폰 사용자 사진에서 확인한 값은 아니다.
- 선명 판정이 흐림으로 바뀌는 경로가 없다. 바뀔 수 있는 사진은 원래 `분석 불가`였던 사진뿐이다.
- 롤백: `sharpness.ts`의 이 변경 하나를 되돌리면 판정 규칙 4로 돌아간다. 저장하는 데이터나 화면 구조 변경이 없다.

## 7. 검증하지 못한 것

- **실제 iPhone Safari·macOS Safari·Firefox·Edge·Android 실기기는 실행하지 않았다.** WebKit 수치는 Windows용 Playwright WebKit(iPhone 15 설정, `OffscreenCanvas` 없음)이다.
- 짧은 실제 손떨림(RealBlur)은 거의 개선되지 않았다(+1장). 일상 손떨림 미검출은 여전히 남아 있다.
- RealBlur 원본은 저장 공간 센스가 2026-11-16에 임시 폴더에서 지웠다. RealBlur는 남아 있는 분석용 이미지 캐시로만 다시 판정했고 브라우저 제품 경로로는 다시 실행하지 않았다.
- 실제 중간 해상도(긴 변 1,100~2,000px) 카메라 원본과 HEIC는 없다.
- 공개 자료의 라벨은 촬영 의도이며 사람이 다시 검토하지 않았다. Kwentar 움직임 흐림은 과장된 흔들림이다.

### iPhone Safari 실기기 확인 목록

이 기록 작성 시점(2026-11-17)에는 모두 미실행이었다. 2026-11-19에 사용자가 iPhone 17 Safari에서 판정 규칙 5가 적용된 웹앱을 직접 실행했다(Issue #27). 아래 상태는 그 관찰 범위만 적는다. 가공 사진의 결과를 실제 촬영 사진의 정확도로 일반화하지 않는다.

| 항목 | 방법 | 상태(2026-11-21 기준) |
|---|---|---|
| 실제 사진 1장·여러 장(30장 이상) 가져오기 | 사진 앱 선택기로 JPEG·HEIC 원본 선택, 추가·건너뜀 수 기록 | **부분 확인**: 가공 JPEG 3장, 가공 JPEG 30장 일괄(`사진 30장을 추가했습니다`), 저장소의 HEIC 시험 파일(160×120) 파일 앱 가져오기·미리보기. **실제 촬영한 고해상도 HEIC 원본은 미확인** |
| 미리보기·크게 비교 | 확대·이동·닫기, 원본 표시 | **확인(가공 JPEG)**: 비슷한 사진 묶기, 크게 비교, 좌우 넘기기, 확대·이동, 남기기, 닫기(사용자 보고). 실제 고해상도 원본에서는 미확인 |
| 흐림 판정·원인 표시 | 흔들린 사진·선명 사진 각 10장 이상에 사람 정답을 붙여 평가 도구(`calibration.html`)로 내보내기 | **부분 확인**: 같은 장면을 가공한 JPEG 3장에서 선명 → 표시 없음, 강한 한 방향 흔들림 → `흔들림 의심`, 강한 초점 흐림 → `초점 불량 의심`. **짧은 실제 손떨림 정확도와 사람 정답 평가는 미확인** |
| 사진당 분석 시간·`timeout`·`failed` | 평가 결과 JSON의 분석 시간과 사유 | 미실행(측정값 없음). 가공 JPEG 30장의 분석 불가 7장은 화면상 `윤곽 부족 또는 잡음`이었고 오류·시간 초과로 확인하지 않음 |
| 대량 가져오기 메모리 | 100장 이상에서 탭 재시작·경고 여부 | 미실행. 가공 JPEG 30장에서는 화면 캡처상 강제 종료 징후 없음. **실제 카메라 원본 대량 처리는 미확인** |
| PC와 판정 일치 | 같은 사진을 PC Chrome과 iPhone에서 내보내 판정·원인 비교 | 미실행 |
| 1,100~2,000px 실제 원본 | 카메라·메신저 저장본 등 실제 중간 해상도 사진 | 미실행 |

짧은 실제 손떨림이 감지되지 않는 원인은 [짧은 실제 손떨림 미검출 원인 분석](sharpness-short-shake-limits.md)에 있다.
