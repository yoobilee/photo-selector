# iPhone 분석 불가 현상 조사와 후속 검증

조사일: 2026-11-08. 기준: `25fb555d9194069941b6022c0a52c37bbe3282c6` (`main`). PR #18 준비 범위의 진단 기록이다.

> 후속: 공개 실제 사진 2,454장으로 기존 판정을 측정하고 개선 후보를 비교한 결과와 판정 규칙 3(분석 불가 사진의 1/2 크기 재판정)은 [공개 실제 사진 기준 흐림 판정 평가](sharpness-real-photo-evaluation.md)에 있다. 아래 내용은 판정 규칙 2 시점의 기록이다.

사용자 보고는 **실제 iPhone 사진 33장 중 20장 분석 불가**다. 20/33(60.6%)은 보고된 발생 비율이지 측정한 정확도가 아니다. 해당 33장의 사진·평가 JSON·사용자 정답은 현재 없으므로 사유별 장수, 어떤 사진이 선명/흐림인지, 20장의 정확한 원인은 확인하지 못했다. README의 과거 18장 평가와 저장소 밖 샘플 관찰을 이 33장의 관찰로 사용하지 않는다. 아래 합성 JPEG 40장의 PC·iPhone 실기기 비교는 별도 평가이며 실제 카메라 사진 33장의 재평가가 아니다.

결론: 기존 calibration 도구의 내보내기에 이미 계산한 방향별 점수만 추가하고 **알고리즘 변경은 보류한다**. 새로운 화면, 임계값 완화, 분석 불가를 선명으로 바꾸는 처리는 추가하지 않는다.

## 1. 분석 불가의 발생 경로

코드 경로: 원본 `File` → `sharpnessWorkerClient` → Worker의 `analyzePhotoImage` → `decodeAnalysisImage` → `measureSharpness` → `classifySharpness`. OffscreenCanvas가 없으면 디코딩·축소만 메인 스레드에서 한 뒤 밝기 배열을 Worker로 보낸다. 평가 도구의 `measure`도 이 경로를 쓴다.

| 사유 | 발생 조건·위치 | 측정값 | 진단 시 구분할 점 |
|---|---|---|---|
| `low-detail` | `classifySharpness`에서 판정 근거 부족 → `evaluateAnalysisImage`가 분석 불가로 매핑 | 있음. 점수는 있을 수도, 없을 수도 있음 | 디코딩·측정은 완료했다. 잡음 과대 추정과 실제 윤곽 부족을 구분해야 함 |
| `too-small` | `getAnalysisSize`가 원본 또는 축소 후 짧은 변 64px 미만/유효하지 않은 크기를 거부 | 없음 | 4000×200 같은 매우 긴 사진도 축소 후 거부됨 |
| `failed` | Worker 안의 디코딩·캔버스·분석 예외, Worker 생성/통신/실행 오류, 메인 스레드 디코딩 실패, dispose 후 호출 등. 큐의 예외도 실패로 정리 | 없음 | 오류 상세는 개인정보 노출을 피하려고 전달하지 않음. 결과 파일만으로 세부 예외는 확정 불가 |
| `unsupported` | 분석기에 Worker 생성 함수가 없음. 기본 경로에서는 `Worker`가 없는 환경 | 없음 | HEIC 미지원·지원하지 않는 파일 형식과 다른 뜻 |
| `timeout` | Worker로 작업을 보낸 뒤 기본 20초 안에 응답이 없음. 해당 Worker를 종료하고 다음 작업은 새 Worker 사용 | 없음 | 큐 대기 시간은 제외. 메인 스레드 사전 디코딩 시간도 제외되므로 전체 20초 제한은 아님 |

가져오기 단계의 `unsupported-format`, `heif-undecodable`, `unreadable`, `duplicate`는 사진을 목록에 추가하지 않는 별도 사유다. 이미 갤러리에 들어온 20장의 `unavailableReason`과 혼동하지 않는다. 이번 작업에서 가져오기·HEIC 경로는 바꾸지 않는다.

### low-detail을 결정하는 근거

- 1024px 이하 분석 이미지를 8×8=64구역으로 나눈다. 1/4 크기에서 방향별 2차 차분 분산을 큰 윤곽의 세기 `structure`로 쓴다.
- `estimateNoise`는 3×3 마스크 응답의 구역별 분산을 정렬하고 하위 25% 위치(64개이면 0부터 세는 15번째)의 분산을 36으로 나눈 뒤 제곱근을 구한다. 하위 25%의 평균이 아니다. 매끈한 구역이 적으면 장면의 미세 질감도 잡음으로 측정한다.
- 잡음 σ에 따른 유효 윤곽 기준은 `max(30, 4 × 6 × σ² / 0.025) = max(30, 960σ²)`다. 잡음 0.3이면 86.4, 1이면 960, 4이면 15,360으로 증가한다.
- 방향마다 윤곽이 30 이상인 구역을 센다. 그중 잡음 기준까지 넘는 유효 구역이 3개 이상이어야 점수를 낸다. 유효 구역의 미세/큰 윤곽 비율 중 높은 3개 평균이 방향 점수이며, 판정한 방향 중 최솟값이 전체 점수다.
- 유효 구역이 3개 미만이고 윤곽 30 이상 구역은 3개 이상이면 `hasUnjudgedDirection=true`다. 점수가 0.025 이상이어도 이 값이 true면 선명으로 확정하지 않는다. 윤곽 30 이상 구역조차 부족한 방향은 점수가 null이어도 이 플래그를 켜지 않는다.
- 판정 우선순위는 낮은 점수로 흐림 → 모든 조건이 일치한 긴 흔들림으로 흐림 → 점수 없음으로 low-detail → 미판정 방향이 남으면 low-detail → 선명이다. 따라서 null 방향 하나만으로 분석 불가가 되지는 않고, 미판정 플래그가 있어도 흐림 근거가 먼저면 흐림이다.
- 큰 원본은 캔버스로 분석 크기 2배까지 그린 다음 2×2 평균으로 축소한다(원본의 가로·세로가 각각 목표의 2배 이상일 때). 그보다 작으면 목표 크기로 바로 그린다. 확대하지 않는다. 브라우저 보간·평균은 약한 흐림과 미세 질감, 잡음의 크기와 상관관계를 함께 바꾼다. 그 뒤 내부의 1/4·1/16 평균 축소가 추가된다.

즉 low-detail은 사진이 나쁘다는 뜻이 아니다. 질감 때문에 잡음 기준이 지나치게 높아졌거나, 실제 잡음이 크거나, 충분한 윤곽이 없거나, 특정 방향의 근거만 부족한 경우를 포함한다. 현재 측정값만으로 센서 잡음과 질감의 원인을 확정할 수 없다.

| 정보 | 기존 화면/내보내기 | PR #18 보완 |
|---|---|---|
| 자동 판정·5종 분석 불가 사유 | 표, JSON, CSV | 유지 |
| 점수·추정 잡음·미판정 방향 존재 여부 | 표, JSON, CSV | 유지 |

| 원본 표시 크기·실제 판별 형식·bpp | 표, JSON, CSV | 유지. 형식은 원본의 시그니처 판별값이며 bpp만으로 JPEG 압축 품질을 확정할 수 없음 |
| 사용자 정답·촬영 조건·장면 번호·출처·검토 여부 | 표에서 지정, JSON/CSV에 기록 | 유지 |
| 기기 설명·분석 경로·선택적 User-Agent | 화면 및 내보내기 | 유지. 기기 설명은 개인정보 없는 모델명/OS/브라우저 버전 정도로 입력 |
| 방향별 윤곽 분산·유효 구역 수 | 실제 실행 결과에는 내보내지 않음 | 이번에는 추가하지 않음. 아래 구역 수는 합성 밝기 배열에서 별도 계산한 조사값 |

사진·썸네일·분석 배열은 앱에서 메모리로만 다루고 서버 업로드·자동 영구 저장을 하지 않는다. 사용자가 내보내기를 눌러 저장하는 것은 평가 데이터다. 화면에는 파일명이 보이지만 결과 파일에는 파일명·경로·EXIF·사진 바이트·해시를 넣지 않는다. 별도의 **정답 데이터** 내보내기는 SHA-256을 포함하므로 기기에 보관하고 진단 결과와 혼동하지 않는다.

JSON 형식 버전은 4, 판정 규칙은 계속 2다. 방향 점수의 순서는 가로, 세로, ↘, ↙다. `[null, 숫자, 숫자, 숫자]`는 일부 방향 미판정, `[null, null, null, null]`은 측정했으나 어느 방향도 판정하지 못함, 배열 자체의 `null`은 측정 없음이다. CSV는 기존 열 순서를 보존하고 방향 열을 끝에 추가한다. 빈 셀 의미는 사유·점수와 함께 해석하며, 버전 정보가 있는 JSON을 진단용으로 우선한다. 기존 파일에 누락된 방향값을 복원할 수는 없다.

표에 새 조작이나 열은 만들지 않는다. 원본은 같은 기기에서만 불러오고, 소스 조사와 기존 네트워크 감시 E2E로 로컬 처리 경로를 확인한다. 이 확인은 실제 iPhone 실험을 대신하지 않는다.

## 3. 합성 재현 결과와 재현하지 못한 범위

재현 대상은 기존 [`blurDetectionLimits.test.ts`](../src/calibration/blurDetectionLimits.test.ts)의 고정 seed·가공 조건이다. 원본 크기가 따로 적히지 않은 장면은 1024×768 밝기 배열이다. 아래는 2026-11-08 Node 24.15.0에서 현재 판정 규칙 2로 다시 측정한 값이다(소수점 반올림). 랜덤 표본이 아니므로 실제 사진 정확도로 해석하지 않는다.

진단용 구역 수는 기존 공개 순수 함수 `downsampleByAverage(image, 4)`와 `regionSecondDifferenceVariance(coarse, 8, dx, dy)`로 구한 64개 값에서 각각 30 이상/`max(30, 960σ²)` 이상을 센 것이다. 방향은 `(1,0),(0,1),(1,1),(1,-1)` 순서다. 위 사례에는 비유한 미세 분산이 없음을 확인했다. 판정 구현에 이 계산을 추가하지 않았다.

- 미세 질감 장면: 윤곽 30 이상 구역은 **58/57/60/60**개 남아 있지만 유효 기준은 **31,574.21**로 올라간다. 방향별 최대 윤곽은 약 **5,133/2,806/8,502/8,446**로 모두 기준 아래다. 윤곽 소실만으로 설명되는 사례가 아니다.
- 잡음 σ4 장면: 윤곽 30 이상은 **57/57/59/59**개지만 유효 기준 **15,242.79** 아래라 모두 제외된다. 미세 질감과 독립 잡음은 같은 결과를 만들었다. 합성 질감 역시 무작위 밝기 변동을 넣은 모델이므로 실제 잎·잔디의 구조를 증명하지 않는다.
- 점수 있는 low-detail도 재현했다. seed 7 흐린 배경 위 선명 가로 줄무늬에 잡음 0.3(seed 3)을 넣으면 방향값은 **null/0.10225/0.10179/0.10172**, 전체 점수 **0.10172**, 미판정 플래그 true로 분석 불가다. 잡음이 없으면 오히려 흐림으로 오탐한다(기존 테스트).

요청한 7종 조건은 합성 또는 근사 모델에서 모두 다시 실행했다. 다만 **실제 iPhone 33장의 재현에는 성공하지 못했다**. 실제 야간 촬영의 신호 의존 잡음·노이즈 제거, 실제 인물의 얼굴/피사체 선명도, 실제 JPEG 인코더, iPhone의 리사이즈·색 관리·메모리/시간 초과는 위 밝기 배열 실험으로 검증하지 못했다. 단순 선명 인물 대조군의 오탐은 이 조건에서 재현되지 않았고, 배경 흐림과 흔들림을 함께 넣을 때의 미검출은 재현됐다. `too-small`·`failed`·`unsupported`·`timeout`의 경계 동작은 기존 단위 테스트 근거이며, 그 테스트로 이번 20장의 사유를 추정하지 않는다.

### 3.1. 합성 JPEG 40장: 실제 PC·iPhone Safari 비교(2026-11-08)

사용자가 동일한 합성 JPEG 40장을 PC와 iPhone Safari에서 분석한 결과를 제공했다. 실제 기기에서 실행했지만 **입력은 합성 사진**이다. 위 순수 밝기 배열 테스트, README의 실제 사진 18장 1차 평가, 최초 보고된 실제 iPhone 사진 33장과 각각 구분한다. 최초 기록은 사용자 제공 비교 집계와 불일치 수치에 근거했다. 후속 Low 지적 수정에서는 로컬에 보관된 PC JSON 원문을 열어 아래 조건별 집계를 재확인했다. iPhone JSON 원문은 확보하지 못했으므로 모바일 수치는 사용자 제공 결과이며 이번에 독립 재집계하지 않았다. 실기기 분석을 다시 실행한 결과도 아니다.

- PC 평가 자료: `blur-evaluation-20261108-150335.json`
- iPhone Safari 평가 자료: `blur-evaluation-20261108-151336.json`
- 사진 대응은 파일 해시 대신 **해상도(`width`, `height`)와 `bitsPerPixel`의 조합**을 사용했다. 이 40장 안에서는 모두 고유하게 일치했으나 **바이트 단위 동일성은 검증하지 않았다**. 이 조합을 일반적인 사진 식별 키로 보장하지 않는다. 세션별 `photo-N`이나 가져온 순서로 대응하지 않았다.
- **PC와 모바일의 정답은 PC 데이터의 정답을 기준으로 위 대응 관계에 연결했다.** iPhone에서 독립적으로 다시 붙인 정답에 대한 평가가 아니다. PC 정답은 선명 17장 / 흐림 19장 / 판단 보류 4장이다.
- 평가용 원본 이미지와 개인 평가 JSON은 커밋하지 않는다. PC 브라우저 버전·iPhone 모델·iOS 버전 등 제공되지 않은 환경 정보는 확정하지 않는다.

| 항목 | PC | iPhone Safari |
|---|---:|---:|
| 분석 완료 / pending | 40 / 0 | 40 / 0 |
| 자동 판정: 선명 / 흐림 / 분석 불가 | 27 / 7 / 6 | 26 / 7 / 7 |
| 정상 판정 / 정답 확정 36장 | 21/36 (58.3%) | 20/36 (55.6%) |
| 손떨림 조건에서 흐림 판정 성공 | 0/6 | 0/6 |
| 초점 흐림 조건에서 흐림 판정 성공 | 6/12 | 6/12 |
| 흐린 사진을 선명으로 판단 | 12장 | 12장 |
| 선명한 사진을 흐림으로 오판 | 0장 | 0장 |

여기서 **감지 성공은 PC 정답 `label === 'blurry'`인 사진의 자동 `verdict === 'blurry'`**다. `condition`은 사람이 지정한 촬영/가공 조건이며 알고리즘이 추정한 원인이 아니다. 따라서 손떨림 조건의 사진을 초점 불량 의심 또는 원인 미확정 흐림으로 판정해도 흐림 감지에는 성공한 것으로 센다. 이 JSON에는 자동 원인 분류 필드가 없으므로 `흔들림 의심`·`초점 불량 의심` 원인 추정의 적중률은 계산하지 않는다. `sharp`와 `unavailable`은 감지 성공에 넣지 않으며, 분석 불가도 조건별 분모에 남긴다.

PC JSON에서 흐림 정답 19장은 손떨림(`camera-shake`) 6장 + 초점 흐림(`out-of-focus`) 12장 + 저조도(`low-light`) 1장으로 나뉜다. 조건 필드는 사진당 하나이며 이 표본에서 세 집단은 겹치지 않는다. 앞의 조건별 18장이 전체 흐림 정답은 아니다. 손떨림 6장은 모두 `sharp`, 초점 흐림 12장은 `blurry` 6장·`sharp` 6장이다. 나머지 **PC `photo-25`는 `condition: low-light`, `label: blurry`, `verdict: unavailable`, `unavailableReason: low-detail`**이며, 1200×900·4.023 bpp다. 저조도 조건이라는 기록만으로 실제 흐림의 물리적 원인을 손떨림이나 초점 불량으로 추정하지 않는다. 해당 모바일 행의 ID·필드는 iPhone 원문 미확보로 직접 확인하지 못했다.

따라서 PC 흐림 정답은 성공 6 + 선명으로 미검출 12 + 분석 불가 1 = 19장이다. 표의 ‘흐린 사진을 선명으로 판단 12장’은 분석 불가를 제외한 미검출 수이며, 분석 불가까지 포함해 흐림 표시를 받지 못한 사진은 PC 기준 13장이다.

**내보낸 JSON에서의 재현 기준**

`photos`의 행을 아래처럼 집계한다. `summary`나 저장된 `outcome`을 그대로 합산하지 않고 정답·조건·판정에서 계산한다. PC에서는 `label`·`condition`을 그대로 쓴다. 모바일은 두 파일의 `format`·`version`·`settings`가 같은지 먼저 확인하고, `JSON.stringify([width, height, bitsPerPixel])` 키가 각 파일 안에서 중복 없이 40개이며 양쪽 키 집합이 동일한지 검사한다. 실패하면 집계를 중단한다. 모바일 `verdict`는 유지하고 PC의 `label`과 `condition`을 연결한 행을 만든 뒤 같은 계산을 적용한다. 모바일 파일 자체의 `summary`·`outcome`은 PC 정답 연결 후의 통계로 간주하지 않는다. 대응은 이 표본 한정이며 바이트 동일성 검사는 아니다.

```js
// rows: PC photos 또는 위 검사·PC 정답/조건 연결을 마친 모바일 행
const blurry = rows.filter(p => p.label === 'blurry')
const countCondition = condition => {
  const group = blurry.filter(p => p.condition === condition)
  return {
    total: group.length,
    detected: group.filter(p => p.verdict === 'blurry').length,
    missedAsSharp: group.filter(p => p.verdict === 'sharp').length,
    unavailable: group.filter(p => p.verdict === 'unavailable').length,
  }
}
// 전체 40행에서 pending이 0인지 확인한 뒤 집계한다.
// PC: camera-shake → 6/0/6/0, out-of-focus → 12/6/6/0,
// low-light → 1/0/0/1 (total/detected/missedAsSharp/unavailable 순서)
```

정상 판정 비율은 `label`이 `sharp` 또는 `blurry`인 36행을 분모로, `verdict === label`인 행을 분자로 센다. 판단 보류 4장만 제외하며 정답이 확정된 사진의 분석 불가도 분모에 남긴다. 분석 완료 40장은 처리 종료를 뜻하며 40장 모두 선명/흐림을 판정했다는 뜻은 아니다. 자동 판정 일치는 대응된 전체 40쌍에서 `PC.verdict === 모바일.verdict`인 쌍의 비율로, **39/40장(97.5%)**은 분석 불가도 포함한다. 높은 기기 간 일치율이 높은 정답률을 뜻하지 않는다. 양쪽이 함께 놓친 흐림 12장과 손떨림 조건의 흐림 판정 성공 0/6이 남아 있으며, 이 합성 표본의 오탐 0건을 실제 사진에서도 오탐이 없다는 근거로 사용하지 않는다.

**유일한 판정 불일치: PC `photo-3` ↔ iPhone `photo-10`**

| 항목 | PC | iPhone Safari |
|---|---|---|
| 판정 / 사유 | `sharp` | `unavailable` / `low-detail` |
| score | 0.2473076041 | 0.2360345187 |
| noise | 1.8668473126 | 2.0601452717 |
| hasUnjudgedDirection | false | true |
| 세로 방향 점수 | 개별 값 미제공 | `null` |

관찰된 차이는 iPhone 쪽 잡음 추정 증가, 일부 방향 미판정과 세로 방향 점수 `null`이다. 두 전체 점수는 모두 선명도 임계값 0.025보다 높으며, iPhone의 미판정 플래그와 `low-detail`은 1절의 판정 경로에 부합한다. 그러나 방향별 윤곽·유효 구역 수가 없어 세로 방향이 왜 미판정됐는지는 확정하지 못한다. **브라우저 차이의 원인을 확정한 결과가 아니다.** 디코딩·색 관리·캔버스 축소 등은 후속 비교 후보일 뿐이며, 입력의 바이트 동일성도 미확인이므로 특정 브라우저 처리만을 원인으로 단정하지 않는다.

대안 A/B/C를 구현하지 않아 전후 정확도 개선량을 제시할 수 없다. D는 계산된 값을 내보낼 뿐으로 판정 차이가 생기지 않는다. 임계값을 낮추거나 low-detail을 sharp로 바꾸는 실험/제품 변경은 하지 않는다.

후속 비교는 같은 사진·기기·브라우저·정답 관찰 배율을 고정하고 정답별 분석 가능 비율, TP/TN/FP/FN, 선명/흐림 각각의 분석 불가 수, 전체 기준 정확도·흐림 재현율·선명 오탐률과 Wilson 95% 구간을 함께 본다. 분석 불가를 제외한 정확도만 올랐다는 이유로 채택하지 않는다. 저조도·질감·인물·압축·원본 크기별 결과와 같은 장면의 선명/흐림 쌍도 비교한다. 조정에 쓰지 않은 사진 묶음을 별도로 남겨 과적합을 확인한다. 허용할 오탐·미검출 손실은 자료를 확인해 사용자와 정한 뒤 알고리즘 변경 및 독립 리뷰를 진행한다.

### 다음 알고리즘 개선의 조사 우선순위

1. **실제 카메라 사진 기준선 확보**: 최초 33장과 별도의 검증 묶음을 합성 평가와 분리한다. 촬영 조건·정답 관찰 배율·기기/브라우저 버전·선택 경로를 기록하고, 가능하면 기기 안에서 해시를 비교해 입력 동일성을 확인한다. 합성 40장만으로 제품 정확도를 보정하지 않는다.
2. **손떨림 미검출과 흐림→선명 오판 우선**: 양쪽 손떨림 0/6, 흐림→선명 12장을 출발점으로 대안 B의 방향/구역 근거와 대안 C의 축소·원본 크롭 비교를 조사한다. 손떨림 원인 추정과 흐림 자체 검출을 구분하고 선명 사진 오탐이 늘어나는지도 함께 측정한다.
3. **잡음·질감과 low-detail 경계 조사**: 대안 A/B를 비교해 전역 잡음 과대·과소 추정과 방향별 근거 부족을 구분한다. 위 한 쌍의 차이는 입력 동일성과 동일 설정을 먼저 확인하고 반복 측정한 뒤 처리 단계별로 좁힌다. 분석 불가를 선명으로 치환하거나 잡음 기준을 일괄 완화하지 않는다.

이는 후속 실험 순서이며 효과가 검증된 해결책은 아니다. 이번 PR에서는 알고리즘·임계값을 변경하지 않는다.

## 5. 실제 사진 검증을 위한 사용자 작업

1. 이 브랜치의 평가 도구를 **같은 iPhone·브라우저**에서 연다. 일반 배포 빌드에는 calibration 화면이 없다. **신뢰할 수 있는 개인 네트워크에서만** 개발 PC의 `npm run calibrate -- --host 0.0.0.0`을 실행한 뒤 같은 Wi-Fi의 iPhone으로 `http://PC의-LAN-IP:5173/calibration.html`을 연다(실제 포트는 Vite 출력 확인). `0.0.0.0`은 개발 서버를 네트워크에 노출하므로 **공용 Wi-Fi에서는 실행하지 않고, 테스트 종료 후 PC 터미널에서 Ctrl+C로 개발 서버를 종료한다.** 화면·자산만 PC에서 받고 사진은 iPhone 브라우저 안에서 처리한다. 기존에 준비된 신뢰할 HTTPS 평가 환경이 있으면 그것을 사용해도 된다. 이번 PR은 배포 설정을 변경하지 않는다.
2. 문제를 봤던 **동일한 33장**을 선택하고 가져오기와 분석이 끝날 때까지 기다린다. 원본을 변환하거나 서버에 업로드할 필요가 없다. 선택한 수와 실제 추가된 수, 건너뛴 형식/중복 등을 구분해 기기에 메모한다. 사진 선택기가 제공한 바이트·크기가 달라지면 최초 관찰과 동일 입력이라는 보장은 없다.
3. 기기·카메라 칸에는 예를 들어 `iPhone 모델 / iOS 버전 / Safari 버전`을 적는다. 사진 앱/파일 앱 중 어느 경로였는지와 앱을 연 방법도 기록한다. User-Agent 포함은 선택 사항이다. 새로고침/화면 이탈 전까지 결과가 메모리에만 있으므로 내보내기를 먼저 마친다.
4. 원본은 기기의 사진 앱에서 확대해 확인하고 도구의 해당 파일명 행에 **선명·흐림·판단 보류**를 직접 붙인다. 자동 판정을 정답으로 쓰지 않는다. 피사체 선명도를 기준으로 배경만 흐린 사진과 구분하고, 화면 맞춤/원본 확대 중 어느 기준인지 함께 메모한다. 촬영 조건, 출처 `real-capture`, 검토함도 채운다. 가능하면 동일 장면의 선명/흐림 쌍에 장면 번호를 붙인다.
5. **평가 결과 JSON**을 내보낸다(우선 권장, 필요하면 CSV도). 사진마다 판정·사유·점수·잡음·방향 점수/null·크기/형식·사용자 정답이 있는지 확인한다. `pending`이 남으면 미완성 자료다. 20장의 사유별 집계, 낮은 점수/점수 없음/일부 방향 미판정을 이 자료에서 먼저 구분한다. 원본 사진은 공유하지 않아도 된다. 결과를 공유할지는 사용자가 결정한다.
6. 같은 사진의 후속 평가를 위해 **정답 데이터**는 기기 안에만 별도 보관한다. SHA-256 연결은 HTTPS/localhost가 필요하므로 위 LAN HTTP에서는 사용할 수 없으며 직접 정답 지정과 평가 결과 내보내기는 가능하다. 정답 데이터에는 해시가 있으므로 공유용 진단 자료로 보내지 않는다. 세션 ID는 다시 불러오면 바뀌므로 서로 다른 세션의 `photo-N`을 사진 대응 키로 쓰지 않는다.
7. 첫 33장은 원인 조사에 사용한다. 실제 성능 판단에는 선명/흐림 각 30장 이상과 여러 조건·기기의 추가 사진, 조정에서 제외한 검증 사진이 필요하다. 이는 최소한의 표본 경고 기준이지 정확도를 보장하는 장수는 아니다. `failed`/`timeout`이 집중되면 동일 파일 소수 장 재시도·브라우저/기기 조건 비교를 별도 기록한다. 재시도 성공만으로 최초 실패를 없던 것으로 처리하지 않는다.

## 6. 이번 PR 범위와 보류 범위

포함: 기존 evaluation JSON/CSV에 방향 점수 추가, 측정 없음/전체/일부 미판정과 원래 수치 보존 테스트, 실제 Worker를 거친 내보내기 E2E, 기존 합성 재현의 방향 미판정 근거 보강, 사용자 제공 합성 JPEG 40장 PC·iPhone 비교 결과, 이 조사와 README 안내. 제품 분석 로직과 classifierRevision은 그대로다.

Draft를 유지하고 관리자 확인 댓글 게시와 병합은 하지 않는다.
