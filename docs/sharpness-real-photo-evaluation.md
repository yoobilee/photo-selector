# 공개 실제 사진 기준 흐림 판정 평가와 개선(판정 규칙 3)

평가일: 2026-11-09~10. 기준 커밋: `cd25ea4`(`main`, 판정 규칙 2). 이 문서는 [iPhone 분석 불가 조사](sharpness-investigation.md)의 후속으로, 실제 카메라 사진 공개 자료로 현재 알고리즘을 먼저 측정하고 개선 후보를 비교한 기록이다.

요약

- 공개 실제 사진 2,454장(같은 장면의 선명·흐림 대응)에서 기존 판정은 **선명 사진 오탐은 거의 없지만(1/1,054), 흐린 사진 대부분을 놓치거나 분석 불가로 남긴다.** Kwentar 사진은 선명 59%, 흐림 72~76%가 분석 불가였다.
- 잡음 추정, 유효 구역 선정, 방향별 흔들림 판단, 축소 크기를 개선용 묶음(dev)에서 비교했다. **오탐을 늘리지 않으면서 효과가 확인된 것은 “분석 불가 사진만 1/2 크기에서 다시 보는 단계적 축소”뿐**이어서 이것만 판정 규칙 3으로 구현했다.
- 최종 검증용 묶음(holdout)에서 Kwentar 초점 흐림 검출 **9.6% → 14.6%**(15 → 23/157), 선명 오탐 **0 → 0**, 판정이 바뀐 사진은 모두 흐림 정답의 `분석 불가 → 흐림 의심`이다. 움직임 흐림(손떨림 포함) 검출과 선명 사진의 분석 불가율은 **개선되지 않았다**.
- 임계값 `0.025`와 기존 판정 기준값은 바꾸지 않았다. 합성 사진에 맞춘 임계값 조정은 하지 않았다.
- 큰 원본은 **기존 코드부터 Chromium과 WebKit의 판정이 14% 달랐다**(브라우저 캔버스 축소 차이, 5절). 이번 변경 후 불일치는 85.7% 일치에서 83.4% 일치로 조금 늘었다. 축소 방식 통일은 후속 과제다.

## 1. 평가 자료

| 자료 | 라이선스 | 내용 | 사용 범위 |
|---|---|---|---|
| [Kwentar Blur Dataset](https://github.com/Kwentar/blur_dataset) ([Kaggle](https://www.kaggle.com/kwentar/blur-dataset)) | CC0(README 표기) | 350개 장면 × 선명(S)·초점 흐림(F)·움직임 흐림(M), 휴대폰 위주 66개 기기 원본 JPEG | 1,050장 전부. 원본 크기(Kaggle 판은 2048px 축소본이라 쓰지 않음) |
| [RealBlur-J](https://github.com/rimchang/RealBlur) (Rim et al., ECCV 2020) | CC BY 4.0 | Sony A7R3 두 대로 같은 순간을 찍은 실제 손 흔들림(blur)·선명(gt) 쌍, 카메라 JPEG에서 잘라 정렬한 PNG(약 680×770) | 234개 장면 × 쌍 번호 1·6·12 = 1,404장 |

- 다운로드: Kwentar는 저자가 README에 공개한 Yandex Disk 미러의 원본 zip(5,022,489,629바이트)을 인증 없이 받았고 공개 메타데이터의 SHA-256 `de5cfe8d…defada`와 일치함을 확인했다. Kaggle API는 인증이 필요해 쓰지 않았다. RealBlur는 Hugging Face의 `RealBlur.tar.gz`를 스트리밍하며 필요한 PNG와 공식 train/test 목록만 풀었다.
- **원본 사진, 평가 목록, 디코딩 캐시, 결과 JSON은 저장소에 커밋하지 않았다.** 모두 세션 임시 폴더에만 두었다. 저장소에는 재현용 스크립트(`scripts/blur-eval/`)와 이 문서의 집계만 남긴다.
- 개선용(dev)과 최종 검증용(holdout)은 **장면 단위**로 나눴다. 같은 장면의 선명·흐림 사진은 항상 같은 쪽이다.
  - Kwentar: 장면 번호의 SHA-256으로 60:40 고정 분할 → dev 193개 장면(579장), holdout 157개 장면(471장)
  - RealBlur: 공식 train 목록 → dev, 공식 test 목록 → holdout. 목록에 없는 2개 장면은 같은 해시 분할을 썼다 → dev 184개 장면(1,104장), holdout 50개 장면(300장)
  - 기기(Kwentar)는 장면과 달리 양쪽에 섞여 있다. 같은 휴대폰의 다른 장면이 두 묶음에 있을 수 있다.
- 정답은 자료 제작자의 촬영 의도 라벨(S/F/M, gt/blur)이며 사람이 다시 검토하지 않았다. RealBlur의 흔들림 사진 중에는 흔들림이 아주 짧은 것도 있다.

### 움직임 흐림을 손떨림과 동일시하지 않는 이유

- Kwentar의 움직임 흐림은 확인한 표본 기준으로 **의도적으로 크게 휘두른 흔들림**이다(1024px 기준 수십 화소 이상). 일상의 짧은 손떨림보다 훨씬 길고, 휘어진 궤적이 많다.
- RealBlur의 흔들림은 노출 중 실제로 카메라를 흔든 사진이지만 렌즈 교환식 카메라, 약 680×770 크롭, 촬영 조건이 제한적이다.
- 따라서 아래의 움직임 흐림 검출률을 휴대폰 사용자의 실제 손떨림 검출률로 읽지 않는다. 판정 원인 표시(`흔들림 의심`)의 적중도 같은 이유로 일반화하지 않는다.

## 2. 평가 방법

재현 순서(데이터 폴더와 결과 폴더는 저장소 밖 임의 경로):

```sh
node scripts/blur-eval/buildManifest.mjs --out <dir>/manifest.json --kwentar <kwentar 폴더> --realblur <RealBlur 폴더>
# 제품 경로 판정(+ 선택: 분석용 밝기 이미지 캐시). --browser chromium | webkit
node scripts/blur-eval/runInBrowser.mjs --manifest <dir>/manifest.json --out <dir>/chromium.json --browser chromium --cache-dir <dir>/cache
node scripts/blur-eval/summarizeBrowserRun.mjs --manifest <dir>/manifest.json --run <dir>/chromium.json [--compare <dir>/webkit.json]
# 캐시로 판정 규칙 후보 비교(Node). --classifier 모듈은 judge(image)를 내보낸다.
node scripts/blur-eval/evaluateCache.mjs --manifest <dir>/manifest.json --cache-dir <dir>/cache --split dev [--classifier <module>]
```

- **제품 경로**: `runInBrowser.mjs`는 Vite 개발 서버와 Playwright로 실제 브라우저를 열고, 사진 파일을 요청 가로채기로만 페이지에 전달한다(외부 전송 없음). 판정은 사용자 화면과 같은 `createSharpnessWorkerAnalyzer().measure()`(Worker 디코딩·측정·판정, 20초 제한)로 했다.
  - PC: Playwright Chromium, Desktop Chrome 설정, 분석 경로 `worker`
  - 모바일 근사: Playwright WebKit, iPhone 15 설정. Windows용 Playwright WebKit에는 `OffscreenCanvas`가 없어 분석 경로가 `main-thread-decode`였다.
- **후보 비교**: 같은 사진을 매번 다시 디코딩하지 않도록 Chromium이 제품의 `decodeAnalysisImage`로 만든 분석용 밝기 이미지를 1/256 고정소수점으로 저장하고 Node에서 판정만 바꿔 비교했다. 고정소수점 오차로 2,454장 중 1~2장의 판정이 브라우저와 달랐다. 아래 **최종 수치는 모두 브라우저 제품 경로 결과**이며 후보 비교 수치는 Node 캐시 결과다.
- 지표: 분석 불가를 분모에 남긴다. 흐림 정답은 `흐림 판정 / 전체`(검출률), 선명 정답은 `흐림 판정 / 전체`(오탐률)와 분석 불가율. 괄호는 Wilson 95% 구간이다.
- 후보는 dev에서만 비교·선택했고, holdout은 선택한 규칙을 구현한 뒤 한 번 측정했다.

### 실패 원인 구분(dev, 진단용 측정값)

1. **분석 불가(low-detail)가 가장 큰 실패다.** 원인은 대부분 잡음 기준이다. 유효 구역 기준 `max(30, 960σ²)` 때문에 추정 잡음 σ가 0.7이면 기준이 약 470, 1.5면 약 2,160이 된다.
   - Kwentar 선명 사진의 추정 잡음 중앙값은 **1.12**로 흐린 사진(초점 0.65, 움직임 0.71)보다 높다. 선명 사진의 미세 질감이 잡음으로 측정되어 판정을 포기한다(기존 문서의 “질감을 잡음으로 보는 한계”가 실제 사진에서 확인됨).
   - 흐린 사진은 큰 윤곽(1/4 크기)까지 약해져, 실제 잡음 수준만으로도 유효 구역이 0개가 된다(분석 불가 흐림 사진의 방향별 최소 유효 구역 수 중앙값 0).
2. **초점 흐림 미검출(선명 판정)**: 점수 분포가 선명 사진과 크게 갈라지지만(Kwentar 초점 흐림 점수 중앙값 0.035, 선명 0.322) 임계값 0.025보다 위에 있다. 원형 초점 흐림, 휴대폰 샤프닝·압축이 합성 가우시안 흐림보다 미세 경계를 더 남기는 것으로 보이며 원인을 하나로 확정하지 못했다. 임계값은 바꾸지 않았다.
3. **움직임 흐림 미검출**: 흔들림 근거 조건 중 실패 사유를 세면 Kwentar 미검출 188장 중 **133장은 근거 구역이 아예 없었다.** 구역마다 “수직 방향은 잡음 기준을 넘게 선명”해야 하는 조건이 실제 잡음에서 거의 성립하지 않는다. 끌린 방향은 윤곽이 사라져 방향 판정에서 빠지고, 남은 방향만으로 `선명` 또는 `분석 불가`가 된다. RealBlur는 흔들림이 짧은 사진이 많아 대부분 점수가 선명 범위다(흔들림 점수 중앙값 0.133, 선명 0.194).

### 채택한 규칙(판정 규칙 3)

- 분석 크기(긴 변 1024px 이하)에서 `판정 근거 부족`일 때만 같은 밝기 이미지를 2×2 평균으로 1/2 크기로 줄여 같은 측정을 한 번 더 한다. 1/2 크기의 짧은 변이 64px 미만이면 하지 않는다.
- 1/2 크기에서 흐림이고, 그 크기의 측정값으로 **흔들림 근거가 모두 일치하거나 기존 초점 불량 추정 기준(`DEFOCUS_*`)이 맞을 때만** `흐림 의심`으로 바꾼다. 원인 표시도 그 크기의 측정값으로 추정한다.
- 1/2 크기에서 선명하거나 원인 근거가 맞지 않으면 `분석 불가`를 유지한다. **분석 불가를 선명으로 바꾸는 경로는 없다.** 분석 크기에서 이미 `선명`·`흐림`이면 1/2 크기는 재지 않는다.
- 근거: 줄이면 독립 잡음의 표준편차가 약 절반이 되어 잡음 기준이 약 1/4로 낮아지고, 1/2 크기에서도 흐린 사진은 원래 크기에서 더 흐리다. 같은 판정은 원래 1/2 크기로 저장된 사진을 분석할 때 이미 쓰는 판정이다.
- 평가 내보내기는 형식 5로 올려 사진별 `halfScale`(1/2 크기의 점수·잡음·미판정 방향·방향 점수)과 CSV `halfScaleScore`·`halfScaleNoise`, 설정 `halfScaleFactor`를 기록한다.

### PC·모바일 일치성(WebKit)

Playwright WebKit(iPhone 15 설정, Windows, 분석 경로 `main-thread-decode`) 제품 경로 결과. 기존 판정은 WebKit에서 같은 제품 함수로 디코딩한 캐시를 Node에서 기존 코드(`main`)로 판정한 값이다(고정소수점 오차 가능).

| 묶음 | 정답 | n | 흐림 판정 기존 → 개선 | 선명 판정(개선) | 분석 불가(개선) |
|---|---|---:|---|---:|---:|
| Kwentar holdout | 선명 | 157 | 0 → 0 | 42 | 115 (73.2%) |
| Kwentar holdout | 초점 흐림 | 157 | 11 (7.0%) → 19 (12.1%) | 16 | 122 (77.7%) |

| 일치 비교(판정·원인 모두 같음) | 기존 | 개선 |
|---|---:|---:|
| RealBlur 1,404장(축소 없음, 약 680×770) | 1,404/1,404 | 1,404/1,404 |
| Kwentar 1,050장(큰 원본 축소) | 900/1,050 (85.7%) | 876/1,050 (83.4%) |

- **큰 원본에서 PC·모바일 판정 불일치는 기존 코드부터 컸다(14%).** 같은 Kwentar 원본의 추정 잡음이 WebKit에서 Chromium의 1.21~1.61배(중앙값 1.30배)였고, 축소가 없는 RealBlur는 1.00배였다. 제품은 원본을 분석 크기의 2배로 캔버스에 그린 뒤 2×2 평균으로 줄이지만, 첫 단계의 브라우저 축소 결과가 다르다. 그 결과 WebKit은 선명 사진의 분석 불가가 더 많다(Kwentar holdout 73.2% vs Chromium 59.2%).
- 개선 후 불일치가 24장 늘었다. 경계에 있는 흐린 사진에서 한 브라우저만 1/2 크기 재판정을 통과한 경우다. 선명 정답 사진에서 새로 생긴 불일치나 오탐은 없다.
- 두 브라우저 각각에서 개선 방향(흐림 정답의 `분석 불가 → 흐림`만 증가, 선명 오탐 0 유지)은 같았다.
- 브라우저에 의존하지 않는 축소(원본을 띠 단위로 원래 크기로 그려 JS에서 면적 평균)는 후속 과제다. 같은 분석용 이미지를 쓰는 비슷한 사진 지문에도 영향을 주므로 별도 PR에서 메모리·시간과 함께 검증해야 한다.
- Windows용 Playwright WebKit의 축소 방식이 iOS Safari와 같은지는 확인하지 못했다.

### 처리 시간

- Node에서 같은 Kwentar 분석용 이미지(1024×768 등)로 측정·판정만 비교: 중앙값 **71.6 → 86.7ms**, 95% 90.5 → 110.1ms, 최대 116.9 → 145.6ms. 1/2 크기 재측정은 Kwentar 1,050장 중 726장(69%)에서 실행됐다.
- Chromium 제품 경로(Worker 디코딩 포함, Kwentar): 중앙값 237 → 293ms, 95% 337 → 410ms, 최대 416 → 573ms. 두 실행은 같은 PC의 다른 시각이라 시스템 부하 차이가 섞여 있다. WebKit(메인 스레드 디코딩 포함, 개선 후): 중앙값 364ms, 95% 587ms, 최대 1,023ms. 20초 제한 대비 여유가 크고 두 브라우저 모두 `timeout`·`failed`는 0장이었다. 실제 휴대폰은 더 느릴 수 있으며 측정하지 않았다.
- 1/2 크기 재측정의 추가 메모리는 분석용 이미지의 1/4 크기 배열(1024×768 기준 약 0.8MB Float32)과 그 1/4·1/16 축소본이다. 원본 크기 화소는 추가로 만들지 않는다.

### 원본 보존

- 변경은 분석용 밝기 배열을 받는 순수 함수(`sharpness.ts`)와 평가 내보내기뿐이다. 가져오기·디코딩·썸네일·내보내기 경로는 바꾸지 않았다. 원본 `File`은 읽기만 하며 1/2 크기 배열은 분석용 배열에서 만든다.
- 기존 E2E의 원본 바이트 보존·외부 요청 감시 검사를 `npm run verify`에서 그대로 통과했다.

## 6. 검증하지 못한 것

- **실제 iPhone Safari·macOS Safari·Firefox·Edge·Android 실기기는 실행하지 않았다.** 모바일 수치는 Windows용 Playwright WebKit(iPhone 15 화면 설정, `OffscreenCanvas` 없음)이며 iOS Safari의 디코딩·색 관리·메모리·속도를 대표하지 않는다. 최초 보고된 실제 iPhone 사진 33장의 재평가도 아니다.
- 공개 자료의 라벨은 제작자의 촬영 의도이고 사람이 다시 확인하지 않았다. 휴대폰 사용자의 실제 사진 분포(인물·야간·HEIC·HDR 처리)와 다르다.
- Kwentar의 움직임 흐림은 과장된 흔들림, RealBlur는 단일 카메라·크롭이다. 실제 손떨림 검출 성능은 이번 평가로 판단할 수 없다.
- RealBlur는 장면당 쌍 3개(1·6·12번)만 사용했다.
