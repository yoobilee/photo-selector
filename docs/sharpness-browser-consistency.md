# 브라우저별 분석용 이미지 축소 차이와 브라우저 독립 축소

평가일: 2026-11-13~15. 기준 커밋: `3d660fe`(`main`, 판정 규칙 3). [공개 실제 사진 평가](sharpness-real-photo-evaluation.md) 5절에서 후속 과제로 남긴 “큰 원본에서 Chromium과 WebKit 판정이 14% 다름”을 조사하고 개선한 기록이다. 변경은 두 가지다.

1. **브라우저 독립 축소**: 분석용 이미지를 브라우저 캔버스로 줄이지 않고 JS로 줄인다(2절).
2. **판정 규칙 4**: 선명 근거가 약하고 초점 불량 근거가 함께 있으면 `선명`으로 확정하지 않고 `분석 불가`로 둔다(6절).

임계값 `0.025`와 흔들림·초점 불량 추정 기준값은 바꾸지 않았다.

## 요약

수치는 모두 Kwentar 1,050장(흐림 정답 700장, 선명 정답 350장), 제품 경로(Playwright Chromium·WebKit) 기준이다. RealBlur 1,404장(원본이 분석 크기 이하)은 두 브라우저·모든 단계에서 판정이 바뀌지 않았다.

| 지표 | `main` Chromium | `main` WebKit | 최종(두 브라우저 같음) |
|---|---:|---:|---:|
| 브라우저 간 판정·원인 일치 | 876/1,050 (83.4%) | ← | **1,050/1,050 (100%)** |
| 흐림 정답의 흐림 판정(검출) | 64 | 44 | 65 |
| 선명 정답의 흐림 판정(오탐) | 1 | 0 | **0** |
| 흐림 정답의 `선명` 판정(놓침) | 138 | 76 | 104 |
| 선명 정답의 분석 불가 | 207 | 258 | 213 |
| 전체 분석 불가 | 705 | 838 | 744 |

1. **브라우저 간 일치**: 원인은 브라우저 캔버스의 축소 보간이었다. JS 축소로 바꾼 뒤 Kwentar 판정·원인 일치는 83.4% → 100%, 잡음 추정 비율(WebKit/Chromium) 중앙값은 1.30 → 1.000이다.
2. **흐림 검출과 오탐**: 흐림 검출은 Chromium 64 → 65장, WebKit 44 → 65장이다. 이 증가는 브라우저 독립 축소에서 생겼고 **판정 규칙 4는 흐림 검출을 바꾸지 않는다.** 선명 사진 오탐은 두 브라우저 모두 0장이다(`main` Chromium의 1장 해소).
3. **판정 규칙 4의 `선명 → 분석 불가` 전환**: 초점 흐림 정답 27장이 `선명`에서 `분석 불가`로 바뀌었다. 선명 정답·RealBlur·합성 선명 장면·E2E의 판정은 바뀌지 않았다. 흐림으로 바뀐 사진은 없다.
4. **기존 WebKit 대비 남은 놓침 증가**: 흐림 정답의 `선명` 판정은 `main` WebKit 76장보다 **28장 많다**(104장, `main` Chromium 138장보다는 34장 적다). 브라우저 독립 축소만으로는 131장이었다. 남은 놓침은 대부분 분석 크기에서 흐림 근거가 보이지 않는 움직임 흐림이다(5·6절).
5. **처리 시간과 메모리**: 분석용 이미지 디코딩 시간 중앙값이 Chromium 2.2배(235 → 511ms), WebKit 1.4배(513 → 726ms)로 늘었다. 24MP 사진 디코딩 중 Chromium 브라우저 메모리 최대 증가량이 약 40~60MB 늘었다(8절).
6. **실제 iPhone Safari는 확인하지 않았다.** WebKit 수치는 Windows용 Playwright WebKit이다(9절).
7. **1,100~2,000px 원본은 실제 사진으로 검증하지 않았다.** Kwentar를 줄여 만든 파생 묶음으로만 확인했다(3절).
8. **판정 규칙 4의 배수 2는 실제 사진 분포에서 고른 경험적 상수다.** 1.5~3배에서 결과가 거의 같아 특정 값에 맞춘 것은 아니지만, 다른 사진 묶음과 실기기에서 다시 검증해야 한다(6절).

## 1. 원인 분리

Kwentar 90장과 RealBlur 6장(장면·종류별 고정 간격 추출)을 Playwright Chromium(Desktop Chrome)과 WebKit(iPhone 15 설정, Windows)에서 같은 페이지 코드로 처리해 단계별 결과를 비교했다.

| 단계 | 비교 대상 | 두 브라우저의 화소가 같은 사진 | 잡음 추정 비율(WebKit/Chromium) | 판정 일치 |
|---|---|---:|---|---:|
| 디코딩 | 원본 크기 1:1 중앙 256×256 밝기 | Kwentar 76/90, RealBlur 6/6 | — | — |
| 기존 제품 축소 | 2배 크기로 캔버스에 그린 뒤 2×2 평균 | 0/90 | 중앙값 1.317 (1.155~1.842) | 82/90 |
| 캔버스 한 번 축소 | 분석 크기로 바로 `drawImage` | 0/90 | 중앙값 2.707 (1.648~3.648) | 64/90 |
| JS 면적 평균 | 원본 1:1 띠 → JS 면적 평균 | 75/90 | 중앙값 1.000 (0.999~1.003) | **90/90** |

- 디코딩 차이가 있던 14장은 모두 iPhone 사진(3024×4032)이고 밝기 차이가 최대 0.89(256단계 중)다. 색 공간(Display P3 → sRGB) 변환 차이로 보이며 확인하지는 않았다. JS 축소 후 차이는 판정에 영향이 없었다.
- 판정 알고리즘은 결정적이다. 축소가 없는 RealBlur는 기존에도 1,404/1,404가 같았다.
- 따라서 차이는 캔버스 축소 보간에서 생긴다. 2배로 그린 뒤 평균하는 기존 완화책은 차이를 줄였지만 없애지 못했다.

## 2. 브라우저 독립 축소

### 방식

`createAnalysisDownsampler`(`src/photos/analysisDownsample.ts`, DOM에 의존하지 않는 순수 모듈):

1. 원본이 분석 크기의 2배 이상이면 2배 크기, 아니면 분석 크기를 중간 크기로 한다(기존 규칙).
2. 원본 RGBA를 중간 크기로 **채널별 면적 평균**한다. 원본 화소가 중간 화소 경계에 걸치면 겹친 면적 비율로 나눈다.
3. 캔버스에서 읽은 값처럼 채널별로 0~255 정수로 반올림한 뒤 밝기(Rec. 601)로 바꾼다.
4. 중간 크기가 2배면 2×2 평균으로 분석 크기로 줄인다.

원본이 분석 크기 이하면 기존 밝기 변환(`toGrayscale`)과 같은 값이다. `decodeAnalysisImage`는 `createImageBitmap`으로 디코딩한 원본을 폭 4,096px·화소 262,144개(RGBA 1MB) 이하 캔버스에 **축소 없이** 옮기고(`imageSmoothingEnabled = false`), 띠 단위로 `getImageData`해 축소기에 넣는다. 원본이 4,096px보다 넓으면 타일로 나눠 읽고 이어 붙인다. 원본 크기 캔버스나 원본 크기 화소 배열은 만들지 않는다. 투명 영역은 기존처럼 흰색 배경 위에 그린다. 원본 `File`은 읽기만 한다.

### 순수 면적 평균을 버리고 기존 구조를 따른 이유

처음에는 원본을 바로 분석 크기의 밝기로 면적 평균했다(부동소수, 8비트 반올림 없음). 실제 사진 전체 평가에서 일치율은 99.9%였지만 `npm run verify`의 E2E 9개(3개 브라우저 × 3개 테스트)가 실패했다. 합성 초점 흐림 사진(`blurred-scene.png`, 1600×1200 가우시안 σ3)이 `초점 불량 의심`에서 `흐림 의심(원인 구분 어려움)`으로 바뀌었다. 방향 점수의 최대/최소 배율이 2.003으로 초점 불량 기준 `DEFOCUS_MAX_SPREAD = 2`를 넘었기 때문이다.

- 기존 경로는 캔버스에서 8비트 값을 읽어 반올림 잡음이 방향과 무관하게 더해졌다. 이 잡음이 미세 경계가 거의 없는 흐린 사진의 방향별 차이를 줄이고 있었다. 순수 부동소수 평균은 이 잡음이 없어 대각선 방향 점수가 상대적으로 낮아졌다.
- 다른 축소 필터를 시험했지만 배율은 모두 더 나빴다(삼각 2.065, 가우시안 2.05~2.10, Lanczos3 2.126, Catmull-Rom 2.128, 안티에일리어싱 없는 쌍선형 2.077, 면적 평균 2.003).
- 판정 기준값은 기존 경로의 분석용 이미지로 정해졌으므로 E2E 기대값이나 기준값을 바꾸지 않고 기존 경로의 구조(1~4)를 그대로 재현해 브라우저별 보간만 바꿨다. 이 방식에서 E2E 9개는 기대값 변경 없이 모두 통과했다.

## 3. 평가 방법

- 자료는 [공개 실제 사진 평가](sharpness-real-photo-evaluation.md)와 같은 2,454장(Kwentar 1,050장, RealBlur 1,404장)과 같은 dev/holdout 분할·정답을 그대로 썼다. 원본·정답·기존 결과·캐시는 수정하지 않았다.
- **변경 전**: 판정 규칙 3 평가의 제품 경로 결과(두 브라우저)를 재사용했다. 재사용 전에 기존 분석용 이미지 캐시를 같은 판정 코드로 Node에서 다시 판정해 대조했고 두 브라우저 모두 2,452/2,454가 같았다.
- **브라우저 독립 축소(판정 규칙 3)**: 제품 경로(`createSharpnessWorkerAnalyzer().measure()`)로 Chromium → WebKit 순서로 한 브라우저씩, 100장 묶음마다 새 Vite 서버·브라우저 프로세스로 2,454장 전체를 실행했다. 묶음 결과는 코드 해시·브라우저·평가 목록 해시·묶음 사진 목록·캐시 경로와 함께 저장하고 모두 같을 때만 재사용했으며, 전체가 끝난 뒤에만 합쳤다. WebKit 실행은 디스크가 가득 차 묶음 022에서 한 번 멈췄고, 완료된 묶음 000~021의 조건을 확인한 뒤 022부터 이어서 끝냈다(중단된 묶음은 결과 파일이 없어 재사용되지 않음). 두 브라우저 모두 실패·시간 초과 0장이다.
- **판정 규칙 4**: 판정은 분석용 이미지의 순수 함수이고, 위 전체 실행과 최종 코드의 차이는 `sharpness.ts`뿐이다(평가 코드 해시로 확인). 그래서 전체 실행이 저장한 두 브라우저의 분석용 이미지 캐시 2,454장씩을 최종 판정 코드로 Node에서 다시 판정했다. 이어서 문제 사진과 대조군 308장을 최종 코드의 제품 경로로 두 브라우저에서 실행해 확인했다(6절). 전체 2,454장 브라우저 실행은 다시 하지 않았다.
- **수치 기준**: 이 문서의 최종 수치는 제품 경로 결과를 기준으로 한다. 판정 규칙 3 전체 실행 결과에 판정 규칙 4가 바꾼 27장(308장 브라우저 실행에서 두 브라우저 모두 확인)을 반영한 값이다. 캐시를 Node에서 다시 판정하면 브라우저 결과와 2,451/2,454가 같다. 다른 3장(`kwentar-201-motion`, RealBlur 2장)은 두 브라우저에서 같은 사진이고 캐시의 1/256 고정소수점 오차로 판정 경계를 넘나든 것이며 판정 규칙 4와는 겹치지 않는다. 앞선 보고의 `전체 분석 불가 717장`(브라우저)과 `716장`(Node 재판정)의 차이가 이 `kwentar-201-motion` 1장이다.
- 분석 경로는 기존과 같다. Chromium `worker`, Windows용 Playwright WebKit `main-thread-decode`(`OffscreenCanvas` 없음).

### 단계 검증과 1,100~2,000px 구간의 한계

전체 평가 전에 (1) 실패하던 E2E 9개와 단위 테스트, (2) 파생 묶음, (3) 96장 표본을 두 브라우저에서 확인했다.

- 평가 자료의 원본은 큰 원본(Kwentar, 긴 변 2,576~6,000px, 중앙값 4,160px)과 분석 크기 이하(RealBlur)로 나뉘어 **실제 중간 해상도(긴 변 1,100~2,000px) 원본이 없다.** 2배 중간 크기 규칙의 경계(긴 변 2,048px)와 1배 경로가 이 구간에 걸린다.
- 그래서 Kwentar 원본을 Chromium 캔버스로 긴 변 1,100·1,280·1,600·2,000px로 줄여 JPEG(품질 0.90)로 저장한 **파생 묶음** 1,050장을 만들어 제품 경로로 확인했다. 파생 사진은 축소 과정에서 흐림이 줄고 브라우저 한 곳의 축소·재압축을 거쳐, 실제 카메라의 중간 해상도 사진을 대표하지 않는다.
- 파생 묶음 결과(판정 규칙 3, 브라우저 독립 축소): 브라우저 일치 862 → 1,050/1,050, 선명 오탐 0 → 0, 흐림 판정 Chromium 67 → 75장, WebKit 40 → 75장. 판정 규칙 4를 같은 캐시에 Node로 적용하면 초점 흐림 정답 63장이 `선명 → 분석 불가`로 바뀌고(흐림 정답의 `선명` 307 → 244장), 선명 정답 판정·오탐·브라우저 일치(1,050/1,050)는 바뀌지 않는다. 파생 묶음은 판정 규칙 4로 제품 경로 실행을 다시 하지 않았다.

### 평가 도구 실패와 수정

순수 면적 평균 시도의 첫 두 실행은 Chromium에서 “Execution context was destroyed, most likely because of a navigation”으로 중단됐다(약 330번째, 304번째 사진). 중단된 사진 단독, 같은 묶음 100장을 다시 실행하면 모두 통과해 특정 사진·메모리 문제가 아니었다. `hmr: false`여도 Vite 클라이언트는 WebSocket을 열고, 연결이 끊기면 서버를 확인한 뒤 `location.reload()`로 페이지를 다시 불러온다(Vite 8.3.5 `client.mjs`). 이 재로딩이 원인으로 가장 유력하지만 확정하지는 못했다. 평가 도구(`scripts/blur-eval/runInBrowser.mjs`)에서 `server.ws: false`로 WebSocket을 끄고 페이지 이동·충돌·Vite 콘솔 메시지를 실행 기록에 남기게 했다. 이후 모든 실행에서 중단과 진단 메시지는 없었다. 제품 코드와는 관계없다.

- 판정·원인 일치(Chromium ↔ WebKit): Kwentar 876/1,050(83.4%) → 1,050/1,050(100%), RealBlur 1,404/1,404 유지. 잡음 추정 비율(WebKit/Chromium, Kwentar) 중앙값 1.300(0.943~2.002) → 1.000(0.983~1.003).
- 축소 변경에서 Chromium이 바뀐 32장은 모두 판정 경계 사진이다. 흐림 정답 64 → 65장(McNemar p = 1.0), 선명 정답의 분석 불가 +6장, 기존 오탐 1장 해소. 원인 판정은 `초점 불량 → 원인 구분 어려움` 1장과 그 반대 1장이 바뀌었다.
- 축소 변경에서 WebKit은 흐림 판정 44 → 65장, 선명 정답의 분석 불가 258 → 213장, 흐림 정답의 `선명` 76 → 131장이 됐다.
- 판정 규칙 4는 두 브라우저에서 같은 초점 흐림 정답 27장을 `선명 → 분석 불가`로 바꿨다. 흐림 판정 수와 원인 표시는 바뀌지 않았다.

## 5. WebKit에서 늘어난 놓침(흐림 → `선명`)의 원인

축소 변경 후 WebKit에서 흐림 정답 사진이 `선명`으로 바뀐 57장(`분석 불가 → 선명` 53장, `흐림 → 선명` 4장)과 반대로 `선명 → 흔들림 의심` 2장을 합친 순증가는 55장이다.

- 57장 중 **56장은 `main`의 Chromium에서도 이미 `선명`**이었고(나머지 1장은 `분석 불가`), 축소 변경 후 Chromium에서도 57장 모두 `선명`이다. 새로 생긴 오판이 아니라 WebKit이 Chromium과 같은 판정으로 수렴한 것이다.
- 기존 WebKit에서 이 사진들의 잡음 추정은 변경 후보다 중앙값 1.41배(1.08~2.03배) 컸다. 잡음이 크면 판정에 쓸 구역의 최소 윤곽 기준이 잡음의 제곱에 비례해 높아져 일부 방향을 판정하지 못했고(`hasUnjudgedDirection`), 그래서 `분석 불가`였다. 잡음 추정이 Chromium과 같아지자 모든 방향이 판정됐고 점수가 임계값 이상이라 `선명`이 됐다.
- 예: `kwentar-1-defocus`는 기존 WebKit 점수 0.0244(`초점 불량 의심`), 변경 후 0.0357, 기존 Chromium 0.0354였다. `kwentar-23-defocus`는 기존 WebKit에서 세로 방향을 판정하지 못했지만 변경 후 네 방향 점수 0.044~0.054로 `선명`이다.
- 즉 기존 WebKit의 `분석 불가`는 흐림 근거가 아니라 캔버스 축소가 키운 잡음 때문이었다. 이 사진들은 분석 크기(긴 변 1,024px)에서 실제로 임계값 이상의 미세 경계를 보인다.
- 다만 흐림 정답의 `선명` 판정 점수는 선명 정답보다 확실히 낮다. 축소 변경 후 `선명` 판정 사진의 점수 중앙값은 흐림 정답 0.063, 선명 정답 0.326이고, 같은 장면 선명 사진 대비 점수 비율 중앙값은 0.14다. 이 차이를 판정 규칙 4에 썼다.

## 6. 판정 규칙 4: 약한 선명 근거 + 초점 불량 근거 → 분석 불가

규칙: 분석 크기 점수가 임계값 이상이지만 `임계값 × SHARP_CONFIRM_FACTOR`(`2`, 즉 0.05)보다 낮고, 같은 측정값이 기존 초점 불량 추정 기준(`DEFOCUS_*`: 서로 수직인 방향 점수가 1.5배 이내, 모든 방향 점수가 2배 이내, 모든 방향이 흐린 구역 3개 이상)을 만족하면 `선명`으로 확정하지 않고 `분석 불가(판정 근거 부족)`로 둔다.

- 흐림으로 바꾸지 않는다. `선명` 확정을 보류하는 용도로만 쓴다. `분석 불가`가 된 사진은 기존처럼 1/2 크기에서 다시 보지만 이 자료에서 그 단계로 흐림이 된 사진은 없었다.
- 임계값 `0.025`, 흔들림·초점 불량 추정 기준값, 1/2 크기 재판정 규칙은 그대로다. 판정 규칙의 판은 4이고 평가 내보내기 `settings`에 `classifierRevision: 4`와 `sharpConfirmFactor: 2`를 기록한다.

### 상수 2의 근거와 재검증 필요성

- 근거는 실제 사진 분포다. 축소 변경 후 Kwentar에서 `선명`으로 판정된 사진의 점수는 선명 정답 137장이 최솟값 0.05 이상(하위 10% 0.126, 중앙값 0.326), 흐림 정답 132장이 하위 25% 0.038·중앙값 0.063이고 132장 중 56장이 0.05 미만이다. 2배(0.05)는 기존 임계값의 정수배 중 선명 정답을 건드리지 않는 가장 큰 값이다.
- 배수 민감도(Node 재판정): 1.5배·2배·3배에서 바뀌는 사진이 20·27·28장이고, 선명 정답·RealBlur 선명 정답의 변화는 0장이다(3배에서만 RealBlur 흔들림 정답 2장이 추가로 바뀜). 결과가 배수에 거의 민감하지 않다. dev와 holdout의 효과(17장, 10장)도 같은 방향이다.
- 그래도 Kwentar·RealBlur 두 공개 묶음에서 고른 **경험적 값**이다. [공개 실제 사진 평가](sharpness-real-photo-evaluation.md) 3절은 “최댓값 < 2×임계값”으로 흐림을 **더 잡는** 안을 dev에 맞춘 새 임계값이라 넣지 않았다. 판정 규칙 4는 같은 크기의 상수지만 흐림을 늘리지 않고 `선명` 확정만 보류하는 보수적 방향이라 채택했다. 다른 기기·장면의 실제 사진, 실제 중간 해상도 원본, 실기기 브라우저에서 다시 검증해야 한다.
- 초점 불량 근거 없이 점수만 보는 단순 띠(`점수 < 임계값 × 2`면 `선명` 대신 `분석 불가`)도 시험했다. 놓침은 132 → 76장(Node 재판정)으로 더 줄지만 합성 선명 장면 50장 중 9장(줄무늬·바둑판·배경 흐림 속 작은 피사체)이 `분석 불가`가 되고, E2E의 선명 블라인드 사진이 `분석 불가`로 바뀌어 기존 E2E가 실패했다. RealBlur 선명 정답 3장도 `분석 불가`가 됐다. 그래서 채택하지 않았다.

### 남은 놓침

움직임 흐림 정답의 `선명` 70장은 바뀌지 않는다. 이 사진들의 점수는 중앙값 0.108(대부분 0.05 이상)이고 모든 방향이 흐린 구역이 없어 분석 크기에서 흐림 근거가 보이지 않는다. 원본 화소 기준으로 작은 흐림이 1,024px로 줄면서 사라지는 기존 한계다. 같은 장면 선명 사진보다 점수가 낮지만(중앙값 0.24배) 사진 한 장만으로는 구분할 기준이 없다. 초점 흐림 정답도 34장이 `선명`으로 남는다.

## 8. 처리 시간과 메모리

같은 세션·같은 페이지에서 기존 디코딩(`main` 코드 그대로)과 새 디코딩을 Kwentar 60장에 번갈아(ABBA) 실행해 각 2회 중 짧은 값을 비교했다. 메인 스레드 기준이다.

| 브라우저 | 기존 중앙값 / 95% / 최대 | 변경 후 중앙값 / 95% / 최대 | 중앙값 비 |
|---|---|---|---:|
| Chromium | 235 / 366 / 393ms | 511 / 745 / 830ms | 2.2 |
| WebKit | 513 / 853 / 921ms | 726 / 1,017 / 1,059ms | 1.4 |

- 원본 전체 화소를 JS로 한 번 훑는 비용이다. 사진 한 장의 20초 제한 대비 여유는 크지만, 수백 장을 가져오면 전체 분석 시간이 그만큼 늘어난다. 실제 휴대폰은 측정하지 않았다.
- 판정 규칙 4의 추가 계산은 해당하는 사진의 1/2 크기 재측정뿐이라 측정 차이가 없었다(308장 실행의 Kwentar 분석 시간 중앙값 Chromium 647ms, WebKit 757ms; 규칙 3 전체 실행 637ms, 735ms).
- 메모리: 24MP 사진 1장을 8회 반복 디코딩하는 동안 브라우저 프로세스 작업 집합의 최대 증가량(대기 상태 대비)은 Chromium 기존 178~191MB → 변경 후 214~249MB, WebKit 264~273MB → 260~273MB다. 띠 크기를 RGBA 4MB에서 1MB로 줄인 결과다. 메모리가 작은 휴대폰에서의 최대 사용량은 측정하지 않았다.

## 9. 검증하지 못한 것과 한계

- **실제 iPhone Safari·macOS Safari·Firefox·Edge·Android 실기기는 실행하지 않았다.** WebKit 수치는 Windows용 Playwright WebKit이다. iOS Safari는 디코더·색 관리·캔버스 크기 제한·메모리가 다를 수 있다. 변경 후에는 캔버스 축소를 쓰지 않으므로 디코딩한 화소가 같다면 결과가 같아야 하지만, 실기기의 디코딩 화소가 같은지는 확인하지 않았다.
- 실제 중간 해상도(긴 변 1,100~2,000px) 원본은 없다. 파생 묶음으로만 확인했다(3절).
- 판정 규칙 4의 배수 2는 경험적 상수이며 다른 사진 묶음에서 재검증이 필요하다(6절).
- 흐림 정답의 `선명` 판정은 104장(15%) 남고, `main` WebKit보다 28장 많다.
- iPhone 사진의 디코딩 차이(밝기 1단계 이내)의 원인은 색 공간 변환으로 추정만 했다.
- 실제 기기의 최대 메모리 사용량과 처리 시간은 측정하지 않았다.
- 평가 도구 중단의 원인(WebSocket 끊김에 의한 재로딩)은 가장 유력한 설명이며 재현으로 확정하지 못했다.
