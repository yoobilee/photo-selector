# Photo Selector

여러 장의 사진에서 실패한 사진과 유사 사진을 구분하고 좋은 사진을 추천하는 웹앱입니다. 최종 선택은 사용자가 합니다.

> 현재 사진 가져오기, 갤러리, 흐릿한 사진(흔들림·초점 불량) 감지와 비슷한 사진 묶기까지 구현되어 있습니다. 눈 감김 분석과 추천 기능은 아직 구현되지 않았습니다.

## 현재 기능

- **사진 가져오기**: 파일 선택기로 여러 장을 선택합니다. JPEG, PNG, WebP만 지원하며 확장자가 아닌 파일 앞부분의 시그니처로 실제 형식을 확인합니다.
- **안전한 건너뛰기**: 지원하지 않는 형식, 손상되어 디코딩할 수 없는 파일, 이미 추가된 사진은 추가하지 않고 사유별로 안내합니다.
- **중복 기준**: 바이트가 완전히 같은 파일을 같은 사진으로 봅니다. 이름이 달라도 내용이 같으면 중복이고, 이름이 같아도 내용이 다르면 다른 사진입니다. 크기가 같은 파일끼리만 내용을 나눠 읽어 비교합니다.
- **갤러리**: 썸네일 그리드와 총 개수를 표시하고 사진 추가와 개별 목록 제거를 지원합니다. 목록 제거는 앱 안에서만 일어나며 기기의 원본 파일은 삭제하지 않습니다.
- **원본 보존**: 선택한 `File` 객체를 그대로 보관합니다. 썸네일은 원본과 분리된 화면 표시용 JPEG 미리보기이며 Object URL은 제거·화면 종료 시 해제합니다. 새로고침하면 목록은 유지되지 않습니다.
- **흐릿한 사진 감지**
  - 사진을 추가하면 기기 안의 Web Worker에서 선명도를 분석합니다.
  - 흐림이 의심되는 사진에는 추정 원인에 따라 `흔들림 의심`, `초점 불량 의심`, 원인을 구분하기 어려우면 `흐림 의심` 표시가 붙습니다. 판정할 수 없는 사진에는 `분석 불가` 표시가 붙습니다. 선명한 사진에는 표시를 붙이지 않습니다.
  - 사진 칸 아래에 짧은 판정 사유(예: `한 방향으로 번진 윤곽`, `분석 시간 초과`)를 직접 보여 줍니다. 마우스를 올리지 않아도 되므로 터치 화면에서도 보입니다. 화면 낭독기는 사진마다 전체 문장을 읽습니다.
  - 갤러리 상단에 진행 상황과 원인별 장수(예: `흔들림 의심 2장 · 초점 불량 의심 1장 · 분석 불가 1장`)를 보여 줍니다.
  - 사진 한 장의 분석이 20초 안에 끝나지 않으면 그 Worker만 종료하고 `분석 불가(분석 시간 초과)`로 표시합니다. 다른 사진의 분석은 계속됩니다.
  - 판정은 참고 정보입니다. 사진을 자동으로 지우거나 바꾸지 않습니다.
- **비슷한 사진 묶기**
  - 바이트까지 같은 파일은 지금처럼 가져오기에서 빠집니다(`이미 추가된 사진`). 그 밖에 화면상 같은 사진과 비슷한 사진을 묶음으로 보여 줍니다.
  - `거의 같은 사진`: 크기·압축·밝기·선명도만 다른 것으로 보이는 사진입니다. 묶음의 모든 사진 쌍이 이 기준을 만족할 때만 이렇게 부릅니다.
  - `비슷한 사진`: 연속 촬영처럼 구도가 비슷하고 조금 움직였거나 일부가 다른 사진입니다. 근거가 약한 쌍이 하나라도 있으면 더 보수적인 이 표현을 씁니다.
  - 갤러리 상단의 `모든 사진` / `비슷한 사진끼리 보기`로 보기를 바꿉니다. 모든 사진 보기는 기존 배열과 조작을 그대로 두고, 묶인 사진 위에 `묶음 N` 표시만 겹쳐 분석 중에도 사진 칸이 움직이지 않습니다.
  - 묶음 보기는 묶음마다 제목과 근거를 보여 주고, 좁은 화면에서도 두 장씩 크게 나란히 놓습니다. 사진 칸·흐림 표시·제거 버튼은 기존 갤러리와 같습니다. 남길 사진은 사용자가 고르고 나머지는 직접 목록에서 제거합니다.
  - 상단에 `비슷한 사진 묶음 2개(5장) · 비교하지 못한 사진 1장`처럼 결과를 보여 줍니다. 분석하지 못했거나 윤곽이 부족하거나 비슷한 후보가 너무 많은 사진은 묶지 않고 `비교하지 못한 사진`으로 셉니다.
  - 사진을 자동으로 지우거나 바꾸지 않습니다. 사진을 추가·제거하면 묶음을 다시 계산합니다.

## 흐림 판정 방식과 한계

**분석 대상**

- 원본을 읽기만 하고, 긴 변 1024화소 이하의 분석용 밝기 이미지를 따로 만들어 판정합니다.
- 원본이 2048화소 이상이면 두 배 크기로 그린 뒤 2×2 평균으로 줄여, 브라우저마다 다른 축소 방식의 영향을 줄입니다. 분석용 화소는 판정 직후 버립니다.

**판정 방법** ([`src/photos/sharpness.ts`](src/photos/sharpness.ts))

1. 사진을 8×8 구역으로 나눕니다.
2. 구역마다 가로·세로·두 대각선 방향의 2차 차분 분산을 두 크기에서 구합니다. 분석 크기에서는 미세 경계를, 1/4 크기에서는 큰 윤곽을 봅니다.
3. 흐림은 미세 경계를 먼저 지우고 큰 윤곽은 남기므로 `미세 경계 / 큰 윤곽` 비율이 작아집니다. 비율을 쓰기 때문에 밝기·대비·해상도에 덜 민감합니다.
4. 방향마다 가장 선명한 3개 구역의 비율을 평균하고, 가장 낮은 방향의 값을 점수로 씁니다.
   - 가장 선명한 구역만 보므로 배경 흐림(아웃포커스)이나 넓은 하늘이 있어도 피사체가 선명하면 선명합니다.
   - 방향별로 보기 때문에 한 방향으로 끌린 흔들림도 찾습니다.
5. 점수가 `0.025` 미만이면 `흐림 의심`입니다.
   - 판정에 쓸 윤곽이 없는 사진(균일한 벽, 매끈한 그라데이션)은 `분석 불가`입니다.
   - 짧은 변이 64화소 미만인 사진, 디코딩 실패도 `분석 불가`입니다. 흐림으로 판정하지 않습니다.
6. 잡음은 미세 경계처럼 보여 흐린 사진을 선명하게 보이게 합니다. 그래서 사진마다 잡음을 추정하고, 잡음이 점수를 임계값 근처까지 올릴 수 없을 만큼 윤곽이 뚜렷한 구역만 씁니다. 윤곽은 있지만 잡음 때문에 판정할 수 없는 방향이 남으면 선명하다고 단정하지 않고 `분석 불가`로 둡니다.
7. 길게 끌린 흔들림은 끌린 방향의 큰 윤곽까지 지워 4의 방향 판정에서 빠집니다(이전에는 `분석 불가`나 `선명`). 그래서 1/16 크기를 함께 보고 아래 근거가 **모두** 일치할 때만 `흔들림 의심`으로 판정합니다. 하나라도 어긋나면 이전 판정을 그대로 둡니다.
   - 근거 구역: 같은 구역에서 수직 방향은 선명한데 끌린 방향은 흐리거나 윤곽이 거의 없고, 1/16 크기에서는 끌린 방향 윤곽이 뚜렷하게(세기 30 이상, 수직 방향의 1/4 이상) 있는데 1/4 크기에서는 그 상대 세기가 4배 이상 약한 구역
   - 근거 구역 6개 이상, 서로 다른 행 3개·열 3개 이상(사진 일부가 아닌 전체의 흔들림)
   - 끌린 방향이 선명한 구역이 하나도 없음
   - 모든 방향이 흐린 구역(배경 흐림·초점 불량)이 근거 구역의 절반 이하
   - 끌린 방향에 수직인 방향의 사진 전체 점수도 선명
   - 줄무늬·수평선처럼 원래 한 방향 윤곽만 있는 장면은 1/16 크기에서도 그 방향 윤곽이 없어 근거가 되지 않습니다.
8. 흐림 의심이면 원인을 추정합니다. 방향별 점수는 보조 근거이며 원인을 확정하지 않습니다.
   - `흔들림 의심`: 7의 근거가 모두 일치합니다.
   - `초점 불량 의심`: 서로 수직인 두 방향(가로·세로, 두 대각선)의 점수가 1.5배 안이고(짝 중 한쪽만 판정하면 제외), 판정한 모든 방향이 2배 안이며, 모든 방향이 흐린 구역이 3개 이상입니다.
   - `흐림 의심`: 어느 쪽 근거도 충분하지 않습니다(비스듬한 흔들림, 흔들림과 초점 불량이 섞인 사진 등).

**임계값 근거**

- 고정 seed로 그린 합성 장면(사각형·원·선·글자 획)을 분석 크기(1024×768)에서 흐리게 해 측정했습니다. 측정은 [`src/photos/sharpness.test.ts`](src/photos/sharpness.test.ts)에 기록돼 있습니다.
- 가우시안 흐림 σ≤1.25화소(원본 4032화소 사진 기준 약 5화소)는 8개 장면 모두 선명입니다.
- σ≥1.75화소(약 7화소)는 모두 흐림이고, 그 사이인 σ=1.5에서는 8개 중 7개가 흐림입니다.
- 흔들림 근거·원인 추정 기준(7·8)은 `0.025` 임계값을 바꾸지 않고 1024×768 합성 장면(seed 6개, 렌즈 흐림 σ0.8 + 잡음 0.3)에서 정했습니다. 실제 사진으로 보정하지 않았습니다.
  - 선명 24장(기본·저대비·배경 흐림·하늘): 모두 선명. 흔들림 근거 구역은 많아야 3개였고 끌린 방향이 선명한 구역은 3~50개였습니다.
  - 방향성이 강한 선명한 장면 102장(가로·세로·기울어진 줄무늬, 바둑판, 벽돌, 수평선, 물결·나뭇결 같은 긴 결, 배경 흐림 위 줄무늬, 잡음 0.3·1): 흐림 의심 0장
  - 가로·세로 흔들림: 9화소는 12장 중 10장, 15·25화소는 24장 모두, 41화소는 12장 중 10장이 `흔들림 의심`입니다.
  - 초점 흐림 σ2·σ3은 12장 모두 `초점 불량 의심`, σ1.5·σ5는 12장 중 8장이 `초점 불량 의심`이고 나머지는 `흐림 의심`입니다.
  - 흔들림을 초점 불량으로, 초점 불량을 흔들림으로 표시한 경우는 없었습니다. 비스듬한(30·45·120도) 흔들림은 `흐림 의심` 또는 `분석 불가`입니다.
  - 이전 판정과 달라진 31장은 모두 흔들림 장면이 `분석 불가`·`선명`에서 `흔들림 의심`으로 바뀐 경우입니다. 선명·방향성·초점 흐림 장면의 판정은 하나도 바뀌지 않았습니다(`sharpness.test.ts`가 이 성질을 검사합니다).

**확인한 오탐·미검출**

- 오탐(선명한 사진을 흐림으로 판정)
  - 개발 중 처음 시도한 방식(가장 선명한 구역의 Laplacian 분산을 고정 임계값과 비교)에서는 다음 사례가 흐림으로 판정됐습니다.
    - 대비를 20%로 줄인 선명한 장면 3개 모두
    - 배경 흐림 속 선명한 피사체 장면 3개 중 1개
  - 현재 방식에서는 다음 사례 모두 오탐이 없습니다.
    - 위 사례들
    - 넓은 하늘 위 선명한 띠
    - 그라데이션 위 선명한 원 하나(`e2e/fixtures` 3개)
    - 균일한 벽·그라데이션(분석 불가)
- 미검출(흐린 사진을 놓침)
  - 흔들림 근거 추가 전 측정(렌즈 흐림 σ0.6, 잡음 없음): 분석 크기에서 5화소 흔들림은 1024×768 합성 장면 8개 중 6개를, 9~15화소 흔들림은 8개 중 1개를, 25화소 흔들림은 8개 중 3개를 놓쳤습니다. 25화소 이상은 흔들림 근거로 대부분 찾습니다(위 임계값 근거).
  - 흔들림 근거를 추가한 뒤에도 배경이 흐린 사진의 긴 흔들림(6장 중 3장 선명, 3장 분석 불가)과 잡음 1 이상인 사진의 긴 흔들림(모두 분석 불가)은 놓칩니다.
  - Chromium·WebKit 실제 브라우저에서 1600×1200 원본의 24화소 흔들림 장면 3개 중 1개는 두 브라우저 모두 놓쳤고, 1개는 WebKit에서만 놓쳤습니다(브라우저의 축소 방식 차이).
  - 1024화소보다 작은 사진은 원래 크기로 분석하므로 흔들림을 덜 찾습니다.

**알려진 한계**

- 실제 카메라 사진 묶음으로 보정하지 않았습니다. 실제 사진에서는 압축 흔적, 휴대폰의 보정·샤프닝, 렌즈 특성에 따라 결과가 달라질 수 있습니다. 실제 사진은 아래 [흐림 판정 평가 도구](#흐림-판정-평가-도구개발용)로 측정합니다([1차 평가 결과](#평가-현황-실제-사진-18장-1차-평가2026-10-30)).
- 큰 사진을 1024화소로 줄여 분석하므로 원본 크기에서만 보이는 약한 흐림은 놓칩니다.
- 길게 한 방향으로 끌린 손떨림은 흔들림 근거가 모두 일치할 때만 찾습니다. 배경 흐림이 많거나 잡음이 많거나 사진이 작아 근거 구역이 적으면 여전히 분석 불가나 선명이 될 수 있습니다.
- 원인 표시(흔들림·초점 불량)는 추정입니다. 가로·세로·두 대각선 4방향만 보므로 비스듬한 흔들림은 원인을 구분하지 못하고 `흐림 의심`이 됩니다. 물결·나뭇결처럼 한 방향으로 긴 결이 사진 전체를 덮고 다른 방향으로 선명한 것이 없으면, 국소적으로 흔들림과 같은 모양이라 흔들림으로 보일 수 있습니다(합성 장면에서는 발생하지 않았습니다).
- 선명한 줄무늬가 강한 배경 흐림 위에만 있고 잡음이 없으면, 줄무늬와 같은 방향의 윤곽이 배경에만 있어 `흐림 의심`이 됩니다(흔들림 근거 추가 전부터 있던 한계, 원인은 흔들림으로 단정하지 않음).
- 분석 시간 제한(20초)은 Worker로 보낸 뒤부터 잽니다. `OffscreenCanvas`가 없어 메인 스레드에서 디코딩하는 브라우저는 디코딩 자체를 중단할 수 없습니다.
- 사진 일부에만 있는 잡음·미세 질감과 강한 JPEG 압축 흔적은 흐린 사진의 점수를 올려 선명으로 판정하게 할 수 있습니다.
- 잡음이 많은 사진(어두운 실내·야간)은 흐림 여부와 관계없이 `분석 불가`가 되기 쉽습니다.
- 사진 전체가 미세한 질감(잔디, 자갈)이거나 아주 선명한 사진도 잡음을 크게 추정해 `분석 불가`가 될 수 있습니다.
- 의도한 배경 흐림만 있고 선명한 피사체가 거의 없는 사진은 흐림 의심으로 표시될 수 있습니다.
- Worker 안에서 `OffscreenCanvas`를 쓸 수 없는 브라우저는 메인 스레드에서 디코딩·축소만 하고 계산은 Worker에서 합니다. Web Worker가 없으면 분석하지 않습니다.

## 비슷한 사진 판정 방식과 한계

**분석 대상**

- 흐림 분석이 이미 만든 분석용 밝기 이미지(긴 변 1024화소 이하)를 같은 Web Worker 작업에서 재사용합니다. 원본을 다시 디코딩하지 않습니다.
- 사진마다 64×64 밝기(4KB), 63비트 pHash, 가로세로 비율만 남깁니다. 지문 계산은 1024×768 기준 약 2.5ms로, 같은 이미지의 흐림 판정(약 107ms)의 2~3%입니다(Node, 개발 PC). 20초 분석 제한에 주는 영향은 작습니다.

**판정 방법** ([`src/photos/photoSimilarity.ts`](src/photos/photoSimilarity.ts))

1. 가로세로 비율이 2% 넘게 다르면 다른 사진입니다.
2. 4×4 구역 중 윤곽이 있는 구역이 6개 미만인 사진(벽, 맑은 하늘, 매끈한 그라데이션)은 비교하지 않습니다. 색·밝기 분포만 비슷한 사진을 묶지 않기 위해서입니다.
3. pHash 거리가 20(63비트 중)을 넘으면 다른 사진입니다. 밝기·대비·해상도·압축에 둔감한 빠른 후보 고르기입니다.
4. 16×16 크기의 윤곽 상관이 0.3 미만이면 다른 사진입니다.
5. 64×64 크기에서 최대 3화소(화면의 약 5%) 이동을 찾아 맞춘 뒤, 4×4 구역마다 평균을 빼고 정규화한 밝기 기울기(윤곽) 상관을 구합니다. 기울기라 밝기를 더해도, 정규화라 대비를 바꿔도 값이 유지됩니다.
6. 윤곽이 있는 구역의 75% 이상이 일치(상관 0.5 이상)하고 전체 상관이 0.5 이상이면 `비슷한 사진`입니다. 일부 구역(표정·움직임)이 달라도 됩니다.
7. 이동이 없고, 전체 상관 0.9 이상, 모든 구역 상관 0.8 이상, pHash 거리 6 이하, 비율 차이 1% 이하이면 `거의 같은 사진`입니다.
8. 기준에 못 미치지만 가까운 쌍(일치 구역 50% 이상, 전체 상관 0.35 이상)은 경계로 두고 묶지 않습니다.
9. 줄무늬·바둑판처럼 자기 자신을 2~3화소 옮겨도 윤곽 상관이 0.8 이상인 반복 무늬는 여러 위치에서 맞아 같은 장면인지 구분할 수 없으므로, 기준을 넘어도 경계로 두고 묶지 않습니다.

**묶음 만들기** ([`src/photos/similarPhotoGroups.ts`](src/photos/similarPhotoGroups.ts))

- 묶음 안의 모든 사진 쌍이 기준을 만족해야 합니다. A-B, B-C만 비슷하고 A-C가 다르면 셋을 한 묶음으로 만들지 않습니다(천천히 옮겨 찍은 사진은 여러 묶음으로 나뉠 수 있습니다).
- 가장 비슷한 쌍부터 합치고, 같은 값이면 지문 내용으로 정한 순서를 씁니다. 두 사진의 비교 방향도 지문 내용으로 정합니다. 그래서 비교가 끝나면 가져온 순서·사진 id와 관계없이 같은 사진 집합은 같은 묶음이 됩니다.
- 새로 분석된 사진만 기존 사진과 한 번씩 비교하고 결과를 기억합니다. 제거된 사진은 비교 결과에서 함께 빠집니다.
- 비교는 메인 스레드에서 8ms 조각으로 나눠 실행하고, 화면은 끝났을 때와 진행 중 250ms마다 갱신합니다.
- pHash 후보가 100장을 넘는 사진(같은 장면을 수백 장 찍은 경우 등)은 비교량과 메모리가 사진 수의 제곱으로 늘지 않도록 비교하지 않고 `비교하지 못한 사진`으로 셉니다. 후보 수는 사진 집합만으로 정해져 순서와 관계없습니다.

**검증 결과(합성 이미지만)**

실제 카메라 사진의 정답 데이터로 검증하지 않았습니다. 아래는 합성 장면([`src/photos/photoSimilarity.test.ts`](src/photos/photoSimilarity.test.ts), [`src/photos/similarPhotoGroups.test.ts`](src/photos/similarPhotoGroups.test.ts), [`e2e/similarPhotos.spec.ts`](e2e/similarPhotos.spec.ts)) 결과이며 실제 사진에서의 정확도를 보장하지 않습니다.

- 거의 같은 사진: 해상도 변경(1024→640·800), JPEG 품질 20~40 흉내와 실제 브라우저 JPEG(품질 0.5), 밝기·대비·감마 변경, 흐림·잡음 추가 모두 `거의 같은 사진`이었습니다.
- 비슷한 사진: 화면의 1.5~4.7% 이동, 6~15% 면적 변경(이동과 함께 포함)은 `비슷한 사진`, 6% 이동이나 25% 면적 변경은 경계(묶지 않음)였습니다.
- 다른 사진: 밝기·대비를 맞춘 서로 다른 장면 45쌍, 크기·각도·주기가 다른 줄무늬·바둑판·벽돌, 같은 수평선 위의 다른 장면, 다른 비율은 묶지 않았습니다. 다른 장면 쌍의 구조 상관은 0.25 미만, 일치 구역 비율은 25% 미만이었습니다.
- 성능 측정용 합성 사진 1,000장(연속 촬영 5장 묶음 120개 + 서로 다른 장면 400장)에서 다른 장면끼리 묶인 경우는 0건이었고, 연속 촬영 9묶음은 처음과 끝 사진의 이동이 비교 범위 끝에 걸려 2+3장으로 나뉘었습니다.

- 앱에서는 분석이 끝난 사진이 한 장씩 들어오고 비교를 8ms 조각으로 나누므로 전체 계산이 한 번에 메인 스레드를 막지 않습니다. 조각은 비교 한 번이 끝난 뒤 시간을 확인하므로 최대 약 12ms까지 넘칠 수 있습니다.
- 최악의 경우 후보가 100장을 넘기 전까지의 사진끼리 묶음 계산이 약 18ms 걸렸습니다.
- 휴대폰 실기기에서는 측정하지 않았습니다. 휴대폰 CPU는 더 느리므로 값이 몇 배 커질 수 있습니다.

**알려진 한계**

- 실제 사진 정답 데이터가 없습니다. 연속 촬영, 같은 장소의 다른 순간, 색이 비슷한 다른 장면, 메신저로 압축된 사본으로 실제 오탐·미탐을 측정해야 합니다.
- 64×64로 비교하므로 큰 형태와 구도가 같고 사진 폭의 1/64보다 작은 세부만 다른 사진은 구분하지 못하고 `비슷한 사진`으로 묶일 수 있습니다(합성 재현 테스트 포함).
- 흐림·잡음 차이는 64×64에서 거의 보이지 않아 `거의 같은 사진`으로 묶입니다. 어느 쪽이 선명한지는 묶음 안의 흐림 표시로 확인합니다.
- 밝기만 비교하므로 색만 다른 사진(흑백 사본 등)도 `거의 같은 사진`으로 묶입니다. 색 기반 판정은 이번 범위에서 제외했습니다.
- 확대·잘라 내기(약 7% 확대 재현 테스트 포함), 좌우 반전, 회전, 5%를 넘는 이동은 같은 장면이어도 묶지 않습니다.
- 같은 크기의 벽돌처럼 약한 반복 무늬는 반복 무늬 판정(9)에 걸리지 않아, 같은 무늬의 다른 벽을 비슷한 사진으로 묶을 수 있습니다.
- 촬영 시각(EXIF)은 쓰지 않습니다. 가만히 둔 카메라로 연속 촬영한 사진은 `거의 같은 사진`으로 묶일 수 있습니다.
- pHash 후보가 100장을 넘는 사진은 비교하지 않습니다.

## 흐림 판정 평가 도구(개발용)

실제 카메라 사진으로 흐림 판정의 정확도를 측정하는 개발자 전용 화면입니다. 판정 알고리즘이나 임계값을 바꾸지 않고, 사용자 화면과 같은 Web Worker·디코딩·판정 경로로 분석한 결과를 사람이 붙인 정답과 비교합니다.

- 열기: `npm run calibrate`로 개발 서버를 실행하면 `/calibration.html`이 열립니다.
  - 배포 빌드(`npm run build` → `dist`)에는 이 화면이 들어가지 않습니다.
  - `npm run build:calibration`은 E2E 검증용 별도 빌드(`dist-calibration`, Git 제외)입니다.
- 사용
  1. 사진을 불러옵니다.
  2. 사진마다 정답(선명·흐림·판단 보류)을 고릅니다. 필요하면 촬영 조건, 같은 장면 번호, 출처(실제 촬영·공개 이미지·인위적 가공)와 정답 검토 여부도 붙입니다.
     - 미리 만든 [정답 데이터](#정답-데이터)가 있으면 `정답 데이터 불러오기`로 한 번에 붙입니다.
  3. 표에서 자동 판정, 점수(`흐림 의심 < 0.025`), 잡음, 분석 불가 사유와 비교 결과를 확인합니다.
  4. 평가 결과를 JSON 또는 CSV로 내보냅니다.
  5. 같은 사진으로 다시 평가할 때를 위해 `정답 데이터 내보내기`로 정답을 저장해 둡니다.
  - 기기·카메라 설명은 직접 입력합니다. 브라우저 User-Agent는 선택한 경우에만 결과에 넣습니다.
- 개인정보
  - 사진은 기기 메모리에서만 처리하고 서버로 보내지 않습니다. 화면을 닫거나 새로고침하면 사진과 정답이 사라집니다.
  - 평가 결과 파일에는 세션 안에서만 의미 있는 평가용 ID(`photo-N`), 정답·촬영 조건·장면 번호·출처 종류·검토 여부, 판정, 점수와 크기·형식·압축률(bpp)만 들어갑니다. 파일 이름·경로·EXIF(위치 등)와 해시는 넣지 않습니다.
  - 파일 이름은 사진을 찾을 수 있도록 도구 화면에만 표시합니다.
  - 평가에 쓴 실제 사진, 내보낸 결과 파일과 정답 데이터 파일은 저장소에 커밋하지 않습니다.

### 정답 데이터

사진마다 정답을 다시 고르지 않도록, 사람이 미리 정한 정답을 사진 파일 내용으로 연결해 한 번에 붙입니다([`src/calibration/groundTruthDataset.ts`](src/calibration/groundTruthDataset.ts)).

- 사진 식별: 원본 파일 바이트의 SHA-256입니다.
  - 브라우저의 Web Crypto로 이 기기에서만 한 장씩 계산하며 원본을 바꾸거나 보내지 않습니다.
  - 세션마다 바뀌는 `photo-N`, 파일 이름과 불러온 순서는 쓰지 않습니다. 이름이 같아도 내용이 다르면 다른 사진이고, 이름만 다른 같은 파일은 가져오기에서 중복으로 빠집니다.
  - Web Crypto는 `localhost`나 HTTPS에서만 동작합니다. 그 밖의 주소(예: 같은 네트워크의 `http://192.168.x.x`)에서는 해시를 계산하지 못한다고 표시하고 정답 데이터를 연결하지 않습니다. 사진 한 장의 해시 계산이 실패하면 그 사진만 연결하지 않고 나머지는 계속합니다.
- 적용 규칙
  - 해시가 일치하고, 정답 데이터 안에서 충돌이 없고, 그 사진을 표에서 직접 고친 적이 없을 때만 적용합니다. 사진 단위로 판단하므로 정답·촬영 조건·장면 번호·출처·검토 중 하나라도 직접 고친 사진은 정답 데이터와 섞지 않고 직접 고친 값을 그대로 씁니다. 정답 데이터와 다르면 `직접 고른 정답 유지(정답 데이터와 다름)`으로 표시하고 개수를 셉니다.
  - 적용된 정답을 표에서 고치면 정답 데이터의 값을 바탕으로 그 사진의 직접 고친 값이 됩니다. 정답 데이터를 닫으면 데이터에서 온 정답만 사라집니다.
  - 일부 사진만 일치해도 나머지는 그대로 평가합니다. 화면에 적용·직접 입력 유지·데이터에 없음·충돌·해시 계산 중·실패 사진 수와, 불러온 사진에 없는 정답 수를 보여 줍니다.
  - 파일을 불러오지 못하면 이유를 보여 주고 이전에 불러온 정답 데이터를 계속 씁니다.
- 파일 검사(다른 사람에게 받은 파일일 수 있으므로 값으로만 읽고 실행하지 않습니다)
  - 5MB, 20,000개 항목까지 읽습니다. `format`·`version`·`hashAlgorithm`·`entries`가 맞지 않으면 파일 전체를 거부합니다.
  - 형식이 틀린 항목은 버리고 개수와 순번을 보여 줍니다(`손상`).
  - 같은 해시·같은 내용이 반복되면 하나만 씁니다(`중복`). 같은 해시에 내용이 다르면 어느 쪽도 적용하지 않습니다(`충돌`, 해시 수).
  - 아는 필드만 새 객체로 옮기며 그 밖의 필드(파일 이름, 판정 등)는 버립니다.
- 내보내기
  - 사람이 고른 정답이 있는 사진만 넣습니다. 자동 판정이나 점수로 정답을 만들거나 판정에 맞춰 바꾸지 않습니다.
  - 정답 데이터를 불러온 상태라면 이번에 불러오지 않은 사진의 항목도 그대로 옮겨 잃지 않습니다. 충돌 항목은 직접 정답을 고른 경우에만 그 정답으로 넣습니다.
  - 항목은 해시 순으로 정렬하고 한 줄에 하나씩 씁니다(아래 예시는 읽기 쉽게 펼친 모양). 파일 이름은 `blur-ground-truth-날짜-시각.json`입니다.
  - 다시 불러올 수 없는 파일은 만들지 않습니다. 항목이 20,000개를 넘거나 파일이 5MB를 넘으면 내보내지 않고 이유를 보여 줍니다. 불러온 정답 데이터에 지금 사진의 정답을 더하면 한도를 넘을 수 있습니다.
- **해시도 식별 정보입니다.** 같은 사진 파일을 가진 사람은 정답 데이터의 해시로 그 사진을 찾아 정답·설명과 연결할 수 있습니다. 정답 데이터는 공유할 때 주의하고 저장소에 커밋하지 않습니다. 같은 안내를 파일의 `notice`에도 넣습니다.
- 평가 결과 파일과의 관계: 평가 결과(`photo-selector-blur-evaluation`)에는 해시가 없고 `photo-N`은 세션마다 바뀌므로 사진과 안전하게 연결할 수 없습니다. 평가 결과를 정답 데이터로 불러오면 거부하고, 사진을 다시 불러와 정답을 고른 뒤 정답 데이터로 내보내도록 안내합니다(자동 변환 없음).

```json
{
  "format": "photo-selector-blur-ground-truth",
  "version": 1,
  "hashAlgorithm": "SHA-256",
  "exportedAt": "2026-10-30T13:56:20.116Z",
  "notice": "각 항목의 sha256은 원본 사진 파일의 내용으로 계산한 값입니다. …",
  "entries": [
    {
      "sha256": "64자리 16진수",
      "label": "blurry",
      "condition": "camera-shake",
      "sceneGroup": 3,
      "origin": "synthetic-edit",
      "reviewed": true,
      "processing": "가로 손떨림 25px",
      "sourceNote": null
    }
  ]
}
```

| 필드 | 값 |
|---|---|
| `sha256` | 필수. 원본 파일 바이트의 SHA-256(대소문자 무관, 소문자로 저장) |
| `label` | 필수. `sharp`, `blurry`, `unsure`(판단 보류) |
| `condition` | 선택. 촬영 조건(`outdoor`, `indoor`, `low-light`, `camera-shake`, `out-of-focus`, `portrait-bokeh`, `landscape-sky`, `texture`, `other`) |
| `sceneGroup` | 선택. 같은 장면을 짝지어 찍은 사진 번호(1 이상 정수) |
| `origin` | 선택. `real-capture`(실제 촬영), `public-image`(공개 이미지), `synthetic-edit`(인위적 가공) |
| `reviewed` | 선택(기본 `false`). 사람이 정답을 다시 확인했는지 |
| `processing` | 선택. 가공 방식(300자 이하). 정답 데이터 파일에서만 고칩니다 |
| `sourceNote` | 선택. 원본 출처(공개 이미지 주소·라이선스 등, 300자 이하). 평가 결과에는 넣지 않습니다 |

평가 결과 형식은 이 변경으로 `version` 2가 되었습니다(사진별 `origin`·`reviewed` 추가, CSV 열도 같은 순서로 추가). 그 밖의 필드는 1과 같습니다.

`version` 3(흔들림 근거 추가)부터 `settings`에 판정 규칙의 판 `classifierRevision`(현재 2)과 흔들림(`shake`)·초점 불량(`defocus`) 기준을 기록합니다. 임계값이 같아도 판이 다르면 같은 사진의 판정이 달라질 수 있으므로 판이 다른 평가 결과는 직접 비교하지 않습니다. `version` 2 이하 결과는 판 1(방향별 점수만으로 판정)의 결과입니다. 사진별 필드와 CSV 열은 바뀌지 않았습니다.

**지표 정의** ([`src/calibration/evaluationMetrics.ts`](src/calibration/evaluationMetrics.ts))

- 양성은 `흐림`입니다.
- 결과 구분
  - 정상: 흐림→흐림 의심, 선명→선명
  - 오탐: 선명→흐림 의심
  - 미탐: 흐림→선명
  - 분석 불가: 정답이 있지만 판정하지 못함
- 판단 보류 라벨과 정답 없는 사진은 정확도 통계에서 빼고 개수만 보여 줍니다. 분석 중인 사진도 끝날 때까지 통계에 넣지 않습니다.
- 판정 가능 비율 = 판정한 사진 / 정답 있는 사진 (전체·선명·흐림 각각)
- 판정한 사진 기준(분석 불가 제외): 정확도, 정밀도(흐림 의심 중 실제 흐림), 재현율, 오탐률. 판정 가능 비율과 함께 봅니다.
- 전체 기준(분석 불가를 분모에 포함하고 맞히지 못한 것으로 계산)
  - 정확도
  - 재현율: 흐린 사진 중 흐림 의심으로 표시된 비율
  - 오탐률: 선명 사진 중 흐림 의심으로 잘못 표시된 비율
- 모든 비율에 Wilson 95% 신뢰구간을 표시합니다. 선명·흐림 정답 중 한쪽이라도 30장 미만이면 참고용으로 표시합니다.

**후속 개선 권고(1차 평가 당시 작성. 3은 흔들림 근거로 일부 반영)**

1. 정답 데이터에 촬영 조건·출처를 채워 정답별 30장 이상으로 다시 평가합니다. 같은 장면의 선명·흐림 짝(`sceneGroup`)을 늘립니다.
2. 큰 사진: 전체 축소본과 함께 가장 선명한 구역을 원본 배율로 잘라 분석하거나, 축소 비율에 따라 점수를 보정합니다.
3. 손떨림: 같은 구역에서 한 방향의 큰 윤곽만 다른 방향보다 크게 약하면 흔들림의 근거로 씁니다. 판정 방법 7로 반영했습니다. 작은 사진은 근거 구역 수 기준을 사진 크기에 맞추는 방법을 실제 사진으로 검토합니다.
4. 잡음: 사진 전체 하나의 추정 대신 구역별 잡음을 추정해 그 구역의 판정 기준에 씁니다. 질감과 잡음은 축소했을 때 줄어드는 정도가 다르므로 둘을 구분합니다.
5. JPEG: 8화소 블록 경계의 차분을 빼거나 약하게 반영합니다.
6. 진단: 평가 결과에 방향별 점수와 판정에 쓴 구역 수를 함께 기록하고, 평가 화면에서 출처·조건별 통계를 나눠 봅니다.

## 계획한 기능

1. **빠른 정리**: 눈 감김 감지(흔들림·초점 불량은 흐림 감지와 원인 추정으로, 비슷한 사진은 묶음으로 구현, 바이트가 같은 중복은 가져오기에서 제외). 비슷한 사진의 실제 사진 검증, 남기기·즐겨찾기와 묶음 단위 정리는 후속 작업입니다.
2. **베스트 컷 추천**: 표정, 선명도, 조명, 구도 등을 고려한 추천
3. **사용자 선택**: 추천 결과 수정, 즐겨찾기, 원본 사진 내보내기
4. **개인화**: 사용자 선택 이력을 반영한 취향 학습(후속 단계)

## 원칙

- 원본 사진은 바이트 단위로 보존합니다. 재압축, 재인코딩, 자동 수정과 자동 삭제를 하지 않습니다.
- 분석은 브라우저 안에서 수행하며 사진을 외부 서버로 전송하지 않습니다.
- 분석용 이미지와 원본 파일을 분리하고, 내보내기에는 원본만 사용합니다.

## 실행 방법

Node.js `^22.22.2 || ^24.15.0 || >=26.0.0`과 npm이 필요합니다. 범위 밖의 Node에서는 `npm ci`가 실패합니다.

```bash
npm ci
npx playwright install chromium webkit   # E2E 테스트를 처음 실행할 때 한 번
npm run dev                              # 개발 서버
npm run calibrate                        # 개발용 흐림 판정 평가 도구(/calibration.html)
```

| 명령 | 내용 |
|---|---|
| `npm run lint` | ESLint |
| `npm run typecheck` | TypeScript 타입 검사 |
| `npm run test` | Vitest 단위 테스트 |
| `npm run build` | 프로덕션 빌드 (`dist/`) |
| `npm run test:e2e` | Playwright E2E. 빌드 결과물을 대상으로 하므로 먼저 `npm run build`가 필요합니다. 평가 도구용 빌드(`dist-calibration`)는 E2E가 직접 만듭니다 |
| `npm run test:gate` | GitHub 리뷰 게이트와 병합 도구 테스트. 병합 도구 테스트는 Linux 전용이라 다른 OS에서는 건너뛰고, CI에서 건너뛰면 실패합니다 |
| `npm run verify` | 위 검사를 모두 순서대로 실행 |

GitHub Actions의 [CI 워크플로우](.github/workflows/ci.yml)가 모든 PR과 `main` push에서 Node 24.15.0으로 `npm ci`와 `npm run verify`를 실행합니다.

### Claude Code에서 Codex 리뷰 요청

Claude Code로 구현한 변경은 [Codex plugin for Claude Code](https://github.com/openai/codex-plugin-cc)로 독립 리뷰를 요청할 수 있습니다. 플러그인은 개발자 컴퓨터에 선택적으로 설치합니다.

- 이 저장소의 `.codex/config.toml`이 Codex 모델(`gpt-6.1-sol`)과 추론 강도(`high`)를 지정합니다. Codex가 이 프로젝트를 신뢰된 프로젝트로 인식할 때만 적용됩니다.
- 역할은 **Claude 구현 → 구현에 참여하지 않은 Codex 검토 → Claude 수정 → 필요한 재검토**로 나눕니다.
- 자동 리뷰(Stop 리뷰 게이트, 저장소 전체 Automatic reviews)는 끄고, 구현과 로컬 검사가 끝난 시점에 `/codex:review --base main`으로 직접 요청합니다.
- PR 전체를 검토할 때는 최신 기준 브랜치와 작업 브랜치의 전체 차이를 대상으로 합니다. 결과에는 base/head 커밋, 검토 범위, 지적사항과 실행하지 못한 검사를 남깁니다.
- 실행 중·취소·스킵·한도 초과는 검토 완료가 아닙니다. 구독 한도에 도달하면 멈추고 유료 API나 추가 결제로 전환하지 않습니다.
- 로컬 로그인 정보와 인증 파일을 저장소에 복사하거나 커밋하지 않습니다.

이 플러그인은 기존 CI, 필요한 독립 검증, PR 결과 기록과 사람 확인을 대체하지 않습니다.

## GitHub 리뷰 게이트

기본 `independent-review` 게이트는 **AI를 호출하지 않고**, 최신 변경에 대한 리뷰 근거와 관리자의 확인 기록을 검사합니다. Codex 리뷰 실행과는 별개의 검사입니다. 자동 병합은 사용하지 않습니다.

게이트는 같은 실행에서 위험도별 **Shadow 판정**도 계산해 Actions Summary에만 남깁니다. Low·Medium·High 자동 판정 후보 여부, 필수 CI, Codex GitHub 리뷰 결과, 사용자 승인, 기존 게이트와의 차이를 보여 주며 병합 조건에는 쓰이지 않습니다. 설정과 판정 기준은 [리뷰 게이트 설정](.ai/checklists/review-gate-setup.md#6-shadow-판정관찰용)에 있습니다.

PR 병합은 개발자 컴퓨터에서 [병합 도구](.ai/checklists/review-gate-setup.md#7-병합-도구)로 squash 병합합니다. 먼저 `node .github/scripts/merge-pr.mjs yoobilee/photo-selector PR번호 --dry-run`으로 위험도, 필수 검사, 리뷰·승인 상태와 병합을 막는 이유를 확인합니다. 병합 도구는 기본 브랜치에 승인된 판정 코드로만 병합하며, 위험도 기준 자동 병합과 Codex 리뷰 자동 요청은 제공하지 않습니다.

PR #10에서는 GitHub가 검사 링크를 `/runs/<check ID>`로 반환해 `/actions/runs/<workflow run ID>`만 허용하던 출처 검증이 정상 검사를 차단했습니다. 실제 API 응답으로 재현한 뒤 두 형식을 각각 해당 ID와 정확히 비교하도록 수정했습니다. 링크가 맞아도 앱·PR HEAD·fingerprint·근거 digest와 실제 workflow 실행 ID·저장소·재실행 횟수·승인된 YAML 검증은 모두 통과해야 합니다. 이 검증은 같은 GitHub Actions 앱의 악의적인 workflow나 유출된 관리자 인증까지 완전히 방어한다는 뜻은 아닙니다.
